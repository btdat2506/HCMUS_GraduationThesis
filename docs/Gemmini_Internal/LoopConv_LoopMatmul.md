# What LoopConv Sends to LoopMatmul and Why

## **WHAT** - Data Sent from LoopConv to LoopMatmul

### **1. Primitive RoCC Commands** 🔧
LoopConv sends a **stream of primitive RoCC commands** generated by its internal functional units:

```scala
// From LoopConv's arbiter output
val unrolled_cmd = arb.io.out  // Arbitrated commands from 5 internal units

// Commands sent to LoopMatmul:
io.out.bits.cmd := Mux(loop_configured, unrolled_cmd.bits, cmd.bits.cmd)
```

**Types of Commands Generated:**
- **LOAD3_CMD** (MVIN): Load data from DRAM to scratchpad
- **STORE_CMD** (MVOUT): Store data from scratchpad to DRAM  
- **PRELOAD_CMD**: Preload weights into systolic array
- **COMPUTE_CMD**: Execute matrix multiplication
- **CONFIG_CMD**: Configure load/store/execute pipelines

### **2. Command Metadata** 📋
Each command includes metadata in the `GemminiCmd` bundle:

```scala
class GemminiCmd extends Bundle {
  val cmd = new RoCCCommand           // The actual RoCC instruction
  val rob_id = UDValid(UInt(...))     // Reorder buffer ID for tracking
  val from_matmul_fsm = Bool()        // Origin: false (not from matmul)
  val from_conv_fsm = Bool()          // Origin: true (from convolution)
}
```

**Key Metadata Fields:**
- **from_conv_fsm = true**: Marks commands as originating from convolution
- **from_matmul_fsm = false**: Distinguishes from matrix multiplication commands
- **rob_id**: Used for completion tracking and resource management

### **3. Command Sources Within LoopConv**
The commands come from LoopConv's 5 internal units via an arbiter:

```scala
arb.io.in(0) <> st.io.cmd          // Store commands (MVOUT, CONFIG)
arb.io.in(1) <> ex.io.cmd          // Execute commands (PRELOAD, COMPUTE, CONFIG)  
arb.io.in(2) <> ld_bias.io.cmd     // Bias load commands (MVIN, CONFIG)
arb.io.in(3) <> ld_weights.io.cmd  // Weight load commands (MVIN, CONFIG)
arb.io.in(4) <> ld_input.io.cmd    // Input load commands (MVIN, CONFIG)
```

## **WHY** - Architectural Reasons for This Interface

### **1. Hierarchical Loop Unrolling** 🏗️

**Problem**: Convolutions require **TWO levels of loop unrolling**:
- **Level 1**: Break convolution into matrix multiplications (LoopConv's job)
- **Level 2**: Break matrix multiplications into `DIM×DIM` tiles (LoopMatmul's job)

**Solution**: Chain LoopConv → LoopMatmul for hierarchical decomposition

```
Convolution (6D loops) → LoopConv → Matrix Multiplications (3D loops) → LoopMatmul → DIM×DIM Operations
```

### **2. Command Type Differentiation** 🏷️

**Problem**: The reservation station needs to distinguish command sources for:
- Resource allocation (different limits for conv vs matmul)
- Completion tracking (separate counters)
- Performance monitoring

**Solution**: `from_conv_fsm` and `from_matmul_fsm` flags enable proper routing:

```scala
// In ReservationStation - separate completion counters
val conv_ld_completed = Output(UInt(...))   // For LoopConv feedback
val matmul_ld_completed = Output(UInt(...)) // For LoopMatmul feedback
```

### **3. Resource Management** 📊

**Problem**: Need to prevent resource conflicts between concurrent conv/matmul operations

**Solution**: LoopMatmul applies additional resource limits and scheduling:

```scala
// LoopMatmul has its own utilization counters
ld_utilization := ld_utilization +& (ldA.io.cmd.fire || ldB.io.cmd.fire || ldD.io.cmd.fire) -& io.ld_completed
```

### **4. Code Reuse and Modularity** 🔄

**Problem**: Matrix multiplication logic is shared between:
- Convolutions (after im2col transformation)
- Direct matrix multiplications (`gemmini_loop_ws`)

**Solution**: LoopConv generates matrix multiplication commands that LoopMatmul can process using the same logic

### **5. Backward Compatibility** 🔙

**Problem**: System must support both high-level convolution operations AND direct matrix multiplication

**Solution**: Command flow supports both paths:

```scala
// In Controller.scala - commands can bypass LoopConv
val (loop_cmd, ...) = LoopMatmul(
  if (has_loop_conv) conv_cmd else raw_cmd,  // Either from LoopConv or direct
  ...
)
```

### **Convolution Command Processing:**
```mermaid

    LC -->|Matrix Mul Commands| LM[LoopMatmul]

```

### **Direct Matrix Multiplication:**
```mermaid

    App[Application] -->|gemmini_loop_ws| CPU[CPU]
    CPU -->|RoCC Commands| LM[LoopMatmul]
    LM -->|Primitive Commands| RS[ReservationStation]
    RS -->|Scheduled Commands| HW[Hardware Controllers]
```

## **Benefits of This Design**

1. **Separation of Concerns**: LoopConv handles convolution-specific logic, LoopMatmul handles matrix tiling
2. **Resource Isolation**: Different operation types have separate resource tracking
3. **Performance Optimization**: Each level can apply specialized optimizations
4. **Debugging Support**: Command origin tracking enables performance analysis
5. **Flexibility**: System can be configured with or without convolution support

This hierarchical design enables Gemmini to efficiently handle both high-level convolution operations and low-level matrix operations while maintaining clean modularity and optimal resource utilization.

\chapter{A SINGLE-CORE RISC-V PROCESSOR SYSTEM WITH A GEMMINI ROCC ACCELERATOR}
\label{chap:SingleCoreGemminiRiscVSystem}

From the surveys and analyses, it is evident that Chipyard effectively meets current requirements, but it also holds the potential for expansion to support more complex systems in the future.

This chapter will present a more detailed exposition of the component structure and the process of constructing an \acrshort{soc} system, while also delving into the architecture of the Rocket processor core. The thesis will utilize high-level design languages \acrshort{chisel}/\acrshort{scala} to implement a single-core processor system integrated with the Gemmini \acrshort{rocc} accelerator, focusing on leveraging the components within an \acrshort{soc} system, and building the hardware and software design based on the Chipyard framework.

\section{The Chipyard Compilation and Elaboration Flow}
\label{sec:chipyard_flow}

A key advantage of the Chipyard framework is its unified compilation and elaboration flow, which decouples high-level hardware design from low-level simulation and implementation targets \cite{chipyard}. The process begins with a \texttt{Custom \acrshort{soc} Configuration}, a set of \acrshort{scala} classes that define the parameters for the entire system. These parameters are consumed by the \texttt{\acrshort{rtl} Generators}---hardware libraries written in \acrshort{chisel}---which programmatically construct the \acrshort{soc} design. Rather than directly emitting Verilog, the \acrshort{chisel} compiler generates a circuit description in the \textbf{\acrshort{firrtl} Intermediate Representation}. This crucial IR acts as a pivot point for the entire framework, allowing a single design description to be consumed by various backend "transforms" tailored for specific goals, as illustrated in Figure~\ref{fig:chipyard_elaboration_flow}.

\begin{figure}[h!]
    \centering
    \includegraphics[width=0.8\textwidth]{Chipyard_ChipyardFlow.pdf}
    \caption[The Chipyard Development and Compilation Flow]{The overall development flow within Chipyard. Design begins with high-level configuration and Chisel generators, which produce FIRRTL. The FIRRTL IR acts as a pivot point, enabling different transformation paths for software simulation, FPGA-accelerated simulation, or VLSI layout. \cite{chipyard}.}
    \label{fig:chipyard_elaboration_flow}
\end{figure}

For instance, the \texttt{FireSim Transforms} can apply modifications necessary for mapping the design onto cloud \acrshortpl{fpga} for fast, cycle-exact simulation. The \texttt{\acrshort{vlsi} Transforms} prepare the design for an \acrshort{asic} implementation flow by replacing logical memories with technology-specific macros and preparing the hierarchy for place-and-route tools.

For the purposes of this thesis, this flow is primarily used to generate synthesizable Verilog for two key targets: 
\begin{enumerate}
    \item \textbf{Software \acrshort{rtl} Simulation:} The \acrshort{firrtl} is compiled into C++ code for cycle-accurate simulation using Verilator, enabling functional verification and initial performance analysis.
    \item \textbf{\acrshort{fpga} Implementation:} The generated Verilog is consumed by the Xilinx \acrshort{vivado} toolchain to be synthesized, placed, and routed for deployment on the target \acrshort{vc707} \acrshort{fpga} board.
\end{enumerate}

This structured flow demonstrates the power of a generator-based approach, allowing a single, high-level design description to target multiple platforms while maintaining design consistency.

\acrshort{chisel} is a Hardware Construction Language (HCL) developed at \acrshort{ucb}, initially intended to enable hardware design through highly parameterized and hierarchically specific code generators \cite{bachrach2012chisel}. \acrshort{chisel} is used to define these generators, which then produce designs in Verilog, suitable for industry-standard \acrshort{rtl} design flows. \acrshort{chisel} is classified as a \acrfull{dsl}; more precisely, it is implemented as a library package for \acrshort{scala}, a high-level, multi-paradigm programming language that integrates features of both \acrfull{oop} and functional programming on the \acrfull{jvm}. Furthermore, \acrshort{scala}'s functional programming capabilities support higher-order functions and immutable data structures, facilitating more maintainable code, which is crucial for reproducibility and collaboration in scientific research.

\acrshort{chisel}'s design aims to address the lack of object-oriented programming and pre-processing structures in existing \acrfullpl{hdl}, supporting the construction of more flexible generators. By being based on \acrshort{scala}, \acrshort{chisel} gains the flexibility to describe hardware with high levels of abstraction and modularity. This helps hardware designers describe circuits in a way that is easy to maintain, modify, and extend, especially for large and complex designs such as microprocessors and specialized digital signal processing cores. \acrshort{scala}'s robust type system, diverse numerical representations and variables, immutability, and support for functional programming make it an ideal foundation for \acrshort{chisel}, aiding in error checking during hardware and circuit description and encouraging reusable design patterns.

In the context of hardware design based on \acrshort{chisel} and \acrshort{scala}, \texttt{sbt} (\acrlong{sbt}) plays a crucial role, optimizing the design management and development process. Built specifically for \acrshort{scala} and Java projects, \texttt{sbt} is the build tool used by the majority of \acrshort{scala} developers. Essentially, \texttt{sbt} acts as the compiler when working with \acrshort{chisel} and \acrshort{scala}. Using \texttt{sbt} simplifies the process of structuring projects for hardware design with \acrshort{chisel} in Chipyard, as well as enabling integration with many other open-source projects.

The design elaboration process using \acrshort{chisel} is illustrated in Figure~\ref{fig:chisel_to_hdl_flow}. A design written in \acrshort{chisel} is first executed by a \acrshort{scala} program, which invokes the \acrshort{chisel} compiler to generate a circuit representation in \acrshort{firrtl}. This intermediate representation is then processed by a series of \acrshort{firrtl} transformers and optimizers, which ultimately produce synthesizable Verilog or VHDL code. This final \acrshort{hdl} can then be consumed by standard industry tools for synthesis and physical design, leading to a final chip layout. This flow abstracts away many tedious aspects of hardware design, allowing architects to focus on the high-level structure and parameterization of their designs.

\subsection{Verilator Simulation Tool}
\label{subsec:verilator}

In the hardware design process, evaluating the functionality of the design is critically important. With Chipyard, system designs, from simple to complex structures, can be effectively realized and tested thanks to integrated tools and \acrshort{rtl} simulators like Verilator, which are readily available within the project framework.

Verilator is an open-source program, prominent in the field of \acrshort{rtl} simulation due to its unique method of converting ("Verilating") \texttt{Verilog} or \texttt{SystemVerilog} into \texttt{C++} or \texttt{SystemC}, creating a highly optimized executable program. Unlike traditional simulators, Verilator does not directly interpret \texttt{Verilog} during simulation. Instead, it generates \texttt{C++} or \texttt{SystemC} program files by parsing the hardware code, performing syntax checking, linting, and optionally inserting debug points and coverage analysis to enhance the correctness and accuracy of evaluation and verification. This "Verilated" output file can be configured to run in single-threaded or multi-threaded mode on a development server, offering an advantage for simulating complex or computationally demanding designs. After the "Verilated" code is generated, it is compiled by a standard \texttt{C++} compiler such as \texttt{GCC}, \texttt{Clang}, or \texttt{MSVC++}, and is typically combined with a user-provided wrapper file to manage the initialization of the Verilated model.

Verilator offers high simulation performance, especially for designs requiring substantial resources, due to its high speed and cycle accuracy. Verilator's compilation approach makes it up to 100 times faster than interpretive simulators like Icarus Verilog (which is also open-source), and with multi-threading, performance can increase by an additional 2-10 times, achieving a total improvement of up to 1000 times. This makes Verilator suitable for \acrshort{riscv} multi-core processor designs ranging from simple to complex, and competitive even with commercial simulators such as Synopsys VCS, Cadence Incisive, or Mentor ModelSim.

\section{The Rocket Processor Core}
\label{sec:rocket_core}

As introduced in the previous chapter, Rocket is a 5-stage, in-order processor core compliant with the \acrshort{riscv} instruction set architecture, with RV32G and RV64G variants. Currently, the development of the Rocket core is maintained by the CHIPS Alliance. Rocket is written in the \acrshort{chisel} hardware design language, based on the \acrshort{scala} programming language, and is a key component of the Rocket Chip \acrshort{soc} Generator toolchain.

When implemented, each Rocket core is combined with L1 data and instruction caches. This memory operates locally for each core and, in a multi-core system, is responsible for storing temporary variables generated during the execution of the pipeline, helping to reduce congestion when multiple cores attempt to store data. Together with the \acrlong{ptw} (\texttt{PTW}), a Tile within the \acrshort{soc} is formed. This Rocket Tile (Figure \ref{fig:rocket_tile_structure}) is considered a fundamental unit in the Rocket Chip \acrshort{soc} system and can be replicated to create multi-core processor systems, meeting the demands for performance and flexibility in modern \acrshort{soc} design.

\begin{figure}[h!]
    \centering
    \includegraphics[width=0.6\textwidth]{Images/RocketTile_Basic.pdf}
    \caption{Structure of a Rocket Tile.}
    \label{fig:rocket_tile_structure}
\end{figure}

Due to the object-oriented nature of \acrshort{chisel}, the language used for its design, Rocket itself is written from object classes that can be defined and reconfigured according to implementation needs, such as \texttt{WithNBigCore()}, \texttt{WithNMedCore()}, \texttt{WithN\allowbreak SmallCore()}, and \texttt{WithNTinyCore()}. Additionally, instead of implementing the Rocket core, the \acrshort{boom} core can also be integrated in its place, and many other peripherals can be integrated into a Tile unit.

\subsection{Bus and Interconnect}
\label{subsec:bus_interconnect}

In the design of \acrfullpl{soc}, bus architecture plays a backbone role, connecting and coordinating the operation of all components within the system. Particularly for modern multi-core processor systems, development trends focus on using crossbar-type bus architectures instead of Time Shared Buses. A crossbar, specifically a fully-connected crossbar structure, is considered a form of hardware switching fabric, allowing any input port to connect directly to any output port simultaneously. The outstanding advantage of this architecture lies in its ability to provide high bandwidth and low latency, effectively meeting performance requirements in applications such as networking equipment, multi-core processors, and high-performance storage systems. The optimization in data transmission offered by this architecture is a key factor in improving the overall performance of modern \acrshort{soc} systems.

For Rocket Chip, the TileLink \cite{sifive2018tilelink} system communication bus was developed concurrently with the project and the \acrshort{riscv} instruction set, and is widely used in open-source system research at present.

\begin{figure}[h!]
    \centering
    \includegraphics[width=0.8\textwidth]{TileLink_Topology.pdf}
    \caption{Connection model in TileLink and its interfaces. \cite{sifive2018tilelink}}
    \label{fig:tilelink_connection_model}
\end{figure}

TileLink is a highly parameterizable, open-source, shared memory interconnect protocol based on the aforementioned crossbar structure, designed to connect diverse modules for \acrshortpl{soc}. TileLink is implemented via a hierarchical, point-to-point network that can be easily scaled. This protocol provides memory-mapped access for multiple controllers, ensuring memory coherency while supporting efficient communication between processors, \acrshortpl{dma}, and peripheral devices.

A TileLink bus system can support a combination of multiple communicating agents, each capable of supporting different configured subsets of the protocol. The TileLink specification includes three levels of operational configuration for agents, presented in Table \ref{tab:tilelink_configs}.

TileLink clearly distinguishes between cached and uncached communications. The simplest level is TileLink Uncached Lightweight (TL-UL), which only supports basic read and write operations to memory, for individual words. The next, more complex level is TileLink Uncached Heavyweight (TL-UH), which adds features such as "hints," "atomic" operations, and burst accesses but does not support coherent caching. Here, "hints" refers to a feature where a request command seeks data information external to the executing command from masters, and "atomic" refers to operations that lock access rights in a system with multiple masters, which could be microprocessors. Finally, TileLink Cached (TL-C) is the full protocol, supporting the use of coherent caches within the system.

For integrating peripheral hardware, all three bus configuration levels can be used. The communication connection diagram, at its most complete level, between a custom peripheral hardware and an agent is shown in Figure \ref{fig:tilelink_channels}.

\begin{figure}[h!]
    \centering
    \includegraphics[width=0.8\textwidth]{TileLink_FiveChannel.pdf}
    \caption{Channels in a TileLink connection between two agents. \cite{sifive2018tilelink}}
    \label{fig:tilelink_channels}
\end{figure}

In this TileLink protocol, the defined communication channels include \texttt{A}, \texttt{B}, \texttt{C}, \texttt{D}, and \texttt{E}, each undertaking specific roles in the interaction process between a master (M) and a slave (S), and all have a defined direction of transmission as depicted in the figure above.
\begin{itemize}
    \item \textbf{Channel A:} This is the initiation channel, where M sends requests to S, establishing the initial step of the communication process.
    \item \textbf{Channel B:} This channel is used when M requests a cache block from S, ensuring necessary data is queried.
    \item \textbf{Channel C:} Used for S to respond to M's request for a cache block, playing a crucial role in providing necessary data to M.
    \item \textbf{Channel D:} This is the general response channel, where S sends the final response to M after processing requests.
    \item \textbf{Channel E:} This channel ensures transaction completion by performing the final handshake for cache block transfer between the two parties.
\end{itemize}

The priority order for these channels is as follows: \texttt{A} < \texttt{B} < \texttt{C} < \texttt{D} < \texttt{E}, where channel \texttt{A} has the lowest priority and \texttt{E} has the highest. Prioritization in the TileLink bus system ensures that messages transmitted through the system do not fall into a hold-and-wait loop. In other words, the message flow through all channels between agents is maintained as a directed acyclic graph, enabling the TileLink protocol to operate without encountering deadlocks, ensuring continuous and uninterrupted data flow within the system.

\subsection{Memory and Cache}
\label{subsec:memory_cache}

Each Tile in the system is integrated with a processor core and an L1 cache that is flexibly configurable. By default design with \acrshort{chisel}, the L1 cache has a size of 16 KiB, organized multi-dimensionally with sets and ways. The L1 cache uses a set-associative cache structure, dividing the memory region into sets, each set containing a fixed number of data blocks (ways). When a memory address access request occurs, the index derived from the address maps it to a specific set. The cache controller then searches for the data block within the ways of that set. This design supports both instruction and data storage, optimizing access performance and increasing the hit rate compared to caches with lower associativity.

In addition to the L1 cache, the system also integrates a shared L2 cache, connected to all cores via the TileLink bus system. The L2 cache acts as an intermediate storage repository, allowing processor cores and other components in the system to perform read/write data requests. This is a coordination mechanism that helps reduce pressure on the main memory and improves overall processing performance. The L2 cache controller also ensures fairness in resource allocation, using a queuing system to manage access requests.

At a higher level, the system also supports the integration of external memory, such as \acrshort{dram} or \acrshort{sram}, through open-source controllers or specialized \acrshortpl{ip} from \acrshort{fpga} implementation toolkits. Additionally, an interface with DRAMSim is supported for integration when performing full-system simulation. This provides flexibility and scalability, meeting various requirements in practical applications.

When external memory is needed in design and simulation, the \acrfull{axi4} interface can be integrated as an intermediate layer, allowing effective connection with \acrshort{dram} or \acrshort{spi} Flash models. To expand the capability of integrating components and peripheral cores to form highly parameterized custom systems suitable for specific applications, the Rocket Chip architecture provides two flexible methods for peripheral integration. Specifically, the system can integrate a peripheral core as a \acrfull{rocc}, located within each tile, or integrate at the system communication level via the \acrshort{mmio} mechanism. These methods facilitate in-depth customization, meeting various requirements for each specific application.

\begin{figure}[h!]
    \centering
    \includegraphics[width=\textwidth]{RocketChip_WithMMIO.pdf}

\acrshort{mmio} Peripherals are custom peripherals attached directly to the TileLink bus, while Tightly-Coupled \acrshort{rocc} Accelerators are custom peripherals attached directly to the arbiter and processor within each Tile, in parallel with the processor core. With the TileLink-Attached \acrshort{mmio} method, the processor communicates with \acrshort{mmio} devices through registers mapped into memory at addresses on the system. Through these registers, control mechanisms or data transfer can be customized to suit the application of the peripheral core. Conversely, in the \acrshort{rocc} Accelerator method, communication is performed via a custom protocol and non-standard \acrshort{isa} instructions, which are configured and defined separately within the encoding space of the \acrshort{riscv} \acrshort{isa}. For Rocket and \acrshort{boom}, each core can control up to four accelerators through custom opcodes, sharing resources with the microprocessor. Instructions executed with \acrshort{rocc} cores have the format \texttt{customX rd, rs1, rs2, funct}. Here, \texttt{X} is a number from 0-3, determining the opcode that controls the routing of the instruction to a specific accelerator. The fields \texttt{rd}, \texttt{rs1}, \texttt{rs2} are the register numbers for the destination register and two source registers, and the \texttt{funct} field is a 7-bit integer that the accelerator can use to differentiate various instructions.

Peripherals connected as \acrshortpl{rocc} have a distinct advantage due to their high customizability and direct connection and control via custom \acrshort{isa} instructions. This allows for specialized performance optimization, particularly useful for cores requiring large, complex computational workloads or applications needing extremely fast response times. Communication via a custom protocol and leveraging the \acrshort{riscv} \acrshort{isa} helps \acrshort{rocc} utilize \acrshort{cpu} resources efficiently, while also offering flexibility in designing specialized accelerator processors. The Gemmini accelerator, central to this thesis, is a prime example of a \acrshort{rocc}-based component, designed for high-throughput matrix multiplication and tightly integrated with the Rocket core.

While \acrshort{rocc} implementation can require a custom software toolchain for its specialized instructions, the performance benefits for demanding applications like those targeted by Gemmini often justify this investment. For this thesis, the integration of the Gemmini accelerator via the \acrshort{rocc} interface is deemed the most appropriate approach to achieve the desired performance for deep learning workloads.

Conversely, the \acrshort{mmio} TileLink-Attached method is widely used for integrating general-purpose memory-mapped peripheral devices. In this model, peripheral devices provide a set of registers (e.g., \acrshort{chisel} Registers) to communicate with microprocessors or other masters on the system bus. This method is suitable for peripherals where the tight coupling and custom instruction set of \acrshort{rocc} are not necessary.

To minimize design complexity for \acrshort{mmio} peripherals, the Rocket Chip architecture provides the \texttt{regmap} interface, which allows for the automatic generation of much of the necessary linking logic. Since TileLink is the official protocol used in \acrshortpl{soc} based on Rocket Chip and Chipyard, designing \acrshort{mmio} peripheral devices (other than the primary \acrshort{rocc} accelerator) would typically focus on integration with this protocol.

\subsection{The RoCC Interface: A Hardware Co-Design Methodology}
\label{subsec:rocc_interface}

The primary conduit for communication between the Rocket Core and the Gemmini accelerator is the \acrfull{rocc} interface. This interface, however, is not merely an external bus; it is a profound hardware \textbf{co-design methodology} that fundamentally alters the \acrshort{cpu}'s own pipeline. When the \texttt{WithGemmini} trait is active in the \acrshort{soc} configuration, the Chipyard generator does more than just instantiate the accelerator; it injects specific logic directly into the Rocket Core's decoder, hazard unit, and writeback stage.

The architectural philosophy of the \acrshort{rocc} interface is designed for high-throughput, decoupled accelerators. As was found in prior work by Pala, the interface's high-latency profile for \acrshort{cpu}-to-accelerator register reads makes it best suited for offloading large, autonomous tasks rather than for frequent, small operations that require constant communication between \acrshort{cpu} and accelerator \cite{pala_master_thesis}. Gemmini, which operates on large data streams for \acrshort{dnn} computation, is a canonical example of this intended use case.

This section will trace the lifecycle of a \acrshort{rocc} instruction to demonstrate how these code-level modifications create a tightly-coupled, low-latency communication channel that is essential for high-performance acceleration.

\subsubsection{The RoCC Instruction Format}
The entire co-design process is initiated by a specific instruction format recognized by the \acrshort{cpu}. The \acrshort{riscv} \acrshort{isa} reserves four major opcodes for custom extensions, and the Gemmini accelerator is assigned the \texttt{custom3} opcode space. Any instruction using this opcode follows the R-type format, modified for \acrshort{rocc} communication as shown in Figure~\ref{fig:rocc_format}.

\begin{figure}[h!]
    \centering
    \includegraphics[width=\textwidth]{Rocket_RoCC_Instruction.pdf}
    \caption{The RoCC Instruction Format. The \texttt{opcode} field is set to \texttt{custom3} (0b1111011). The \texttt{funct7} field specifies the Gemmini-specific operation, while the \texttt{xd}, \texttt{xs1}, and \texttt{xs2} bits act as control signals for the hardware interface.}
    \label{fig:rocc_format}
\end{figure}

The fields in this instruction format are critical for orchestrating the hardware interaction:
\begin{itemize}
    \item \textbf{\texttt{opcode}}: Identifies the instruction as a \acrshort{rocc} command, directing it away from the standard execution units.
    \item \textbf{\texttt{funct7}}: This 7-bit field is passed directly to Gemmini, which uses it to select the specific operation to perform (e.g., \texttt{LOOP\_CONV\_WS}, \texttt{CONFIG\_LOAD}).
    \item \textbf{\texttt{xd, xs1, xs2}}: These single-bit fields are essential hardware control signals. They function as "valid" bits for the register operands. \texttt{xs1} and \texttt{xs2} signal that valid data is present on the \texttt{rs1} and \texttt{rs2} buses, while \texttt{xd} signals that the \acrshort{cpu} expects a result for the destination register \texttt{rd} and must stall until a response arrives.
\end{itemize}

\subsubsection{Modifying the CPU's Instruction Decoder}
For the co-design to function, the \acrshort{cpu} must first be taught to recognize the new instruction format. The Chipyard generator achieves this by programmatically modifying the main decoder table in the Rocket Core, as shown in Listing~\ref{lst:decode_mod}.

\begin{lstlisting}[language=scala, caption={Modification of the Rocket Core's instruction decode table.}, label={lst:decode_mod}, captionpos=b]
// From rocket-chip/src/main/scala/rocket/IDecode.scala
CUSTOM3 -> List(Y,N,Y,N,N,N,N,N,A2_ZERO,A1_RS1,IMM_X,DW_XPR,...),
\end{lstlisting}
This modification is the first and most critical step. It instructs the decoder that the \texttt{custom3} opcode is a valid instruction that uses the register file (as specified by \texttt{A1\_RS1}) but not the standard \acrshort{alu}. This prevents the \acrshort{cpu} from triggering an illegal instruction trap and instead flags the instruction internally as a \acrshort{rocc} command, allowing it to propagate down the pipeline for specialized handling, as illustrated in Figure~\ref{fig:rocc_flow}.

\begin{figure}[h!]
    \centering
    \includegraphics[width=\textwidth]{Rocket_RoCC_Flow.pdf}
    \caption{Diagram illustrating the RoCC co-design and control flow. (1) A RoCC instruction is recognized at the Decode stage. (2) At the Writeback stage, the \texttt{RoCCCommand} is dispatched to Gemmini over a \texttt{ready/valid} channel. (3) A \texttt{busy} signal provides back-pressure to the CPU's Hazard Unit, stalling the pipeline. (4) The \texttt{resp} path provides a privileged write-back directly to the Register File.}
    \label{fig:rocc_flow}
\end{figure}

\subsubsection{Pipeline Integration and Hazard Management}
The tight coupling between the \acrshort{cpu} and Gemmini necessitates new hardware interlocks to manage pipeline hazards. These interlocks are injected directly into the \acrshort{cpu}'s control logic. If Gemmini is busy and cannot accept a new command, it exerts \textbf{back-pressure} on the \acrshort{cpu}. The hardware logic shown in Listing~\ref{lst:stall_logic} generates a stall signal that freezes the \acrshort{cpu} pipeline until the accelerator is ready.

\begin{lstlisting}[language=scala, caption={RoCC-specific stall logic in the Rocket Core.}, label={lst:stall_logic}, captionpos=b]
// Source: rocket-chip/src/main/scala/rocket/RocketCore.scala

// Stall decode if RoCC is not ready for a new command
val rocc_blocked = Reg(Bool())
rocc_blocked := !wb_xcpt && !io.rocc.cmd.ready && 
                (io.rocc.cmd.valid || rocc_blocked)

// Replay the instruction in the writeback stage
val replay_wb_rocc = wb_reg_valid && wb_ctrl.rocc && 
                     !io.rocc.cmd.ready
\end{lstlisting}
This logic provides definitive proof of a hardware co-design. The \texttt{replay\_wb\_rocc} signal physically stalls the \acrshort{cpu} pipeline if a command is in the writeback stage and Gemmini is not ready (\texttt{!io.rocc.cmd.ready}). Furthermore, the \texttt{rocc\_blocked} register freezes the pipeline at the decode stage if a new \acrshort{rocc} instruction arrives while the accelerator is already busy. The \acrshort{cpu}'s progression is now physically dependent on the state of the accelerator.

\subsubsection{The Privileged Response Path}
Finally, the \acrshort{rocc} interface provides a privileged, low-latency path for the accelerator to write results back into the \acrshort{cpu}'s register file. This is arbitrated with other internal units, as shown in Listing~\ref{lst:resp_path}.

\begin{lstlisting}[language=scala, caption={RoCC response handling in the Rocket Core.}, label={lst:resp_path}, captionpos=b]
// Source: rocket-chip/src/main/scala/rocket/RocketCore.scala
when (io.rocc.resp.fire) {
  div.io.resp.ready := false.B // Disable div response
  ll_wdata := io.rocc.resp.bits.data
  ll_waddr := io.rocc.resp.bits.rd
  ll_wen := true.B
}
\end{lstlisting}
When the Gemmini accelerator has a result, the hardware routes the response data (\texttt{io.rocc.resp.bits.data}) directly to the register file's write port (\texttt{ll\_wdata}) and asserts the write enable signal (\texttt{ll\_wen}). This is a privileged write path that completely bypasses the memory system, a feature impossible to achieve with a standard peripheral.

\subsubsection{The RoCC Memory Interface}
Beyond the command interface, the \acrshort{rocc} protocol provides a privileged, high-bandwidth connection directly to the \acrshort{cpu}'s L1 Data Cache, shown in Figure~\ref{fig:rocc_mem_iface_asym}. This is a key advantage over a standard memory-mapped peripheral, which would suffer from the higher latency of the L2 cache and system bus.

\begin{figure}[h!]
    \centering
    \includegraphics[width=0.6\textwidth]{Rocket_RoCC_Interfaces_mem.pdf}
    \caption{The asymmetrical RoCC memory interface. The request channel (\texttt{mem\_req}) uses a full \texttt{ready/valid} handshake, while the response channel (\texttt{mem\_resp}) is a simpler \texttt{valid}-only interface.}
    \label{fig:rocc_mem_iface_asym}
\end{figure}

Critically, this interface is asymmetrical. The request channel from Gemmini to the L1 D-Cache (\texttt{mem\_req}) is a full \texttt{Decoupled} interface, allowing Gemmini to wait if the cache is busy. However, the response channel from the L1 D-Cache to Gemmini (\texttt{mem\_resp}) has only a \texttt{valid} signal. This is a deliberate design choice: the accelerator cannot apply back-pressure to the L1 D-Cache and must accept memory responses immediately to prevent stalling the main \acrshort{cpu} pipeline. This nuance highlights the deeply integrated nature of the memory co-design. As confirmed by the timing analysis in Figures \ref{fig:rocc_mem_timing_single} and \ref{fig:rocc_mem_timing_multiple}, this interface exhibits a two-cycle latency and a maximum throughput of 50\%, performance characteristics that must be considered when designing and scheduling operations for the accelerator

\subsubsection{Conclusion}
In summary, the \acrshort{rocc} integration is a profound act of hardware co-design, proven by the evidence from the hardware generator. The process modifies the \acrshort{cpu}'s instruction decoder, injects new stall conditions into the core hazard unit, provides a privileged response path to the register file, and grants direct, arbitrated access to the L1 cache. These code-level modifications create the tightly-coupled, high-performance link necessary to realize the performance uplift for \acrshort{dnn} workloads, which will be quantified in Chapter \ref{chap:fpga_results}. 

With the hardware co-design methodology now established as the mechanism for integrating our accelerator, the next chapter will explore the architectural foundations of \acrfull{dnn} acceleration to understand why such specialized hardware like Gemmini is required in the first place.

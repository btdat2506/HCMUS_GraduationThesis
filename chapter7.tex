\chapter{System Implementation and Testing}
\label{chap:implementation}

This chapter details the implementation of the RISC-V System-on-Chip (SoC) featuring a Gemmini accelerator. We will cover the hardware configuration using the Chipyard framework, the internal architecture of the Gemmini accelerator itself, its integration as a RoCC (Rocket Custom Coprocessor) unit, the software stack required to boot a full Linux operating system, the automated build process, and finally, the verification of the system on a Xilinx VC707 FPGA board.

\section{Hardware Implementation: SoC Configuration}
The foundation of our hardware design is the Chipyard SoC generation framework, which provides a flexible and powerful environment for constructing complex RISC-V systems. We leverage Chipyard to define a custom SoC that includes a 64-bit Rocket Core alongside the Gemmini accelerator.

\subsection{The \texttt{Rocket64b1gem16} Configuration}
The specific configuration for our SoC is named \texttt{Rocket64b1gem16}. This name concisely describes its key features: a 64-bit Rocket Core (\texttt{Rocket64}), one "big" core (\texttt{b1}), and a 16x16 Gemmini systolic array (\texttt{gem16}). This configuration is defined in Scala using Chipyard's \texttt{Config} classes, which employ a mixin-based approach to compose system components.

The core of the configuration is shown in Listing \ref{lst:rocket64b1gem16_config}. It inherits from a \texttt{BaseConfig} and adds a series of traits (mixins starting with \texttt{With...}) that customize the final SoC.

\begin{lstlisting}[language=Scala, caption={The \texttt{Rocket64b1gem16} configuration class.}, label=lst:rocket64b1gem16_config]
class Rocket64b1gem16 extends Config(
  new WithGemmini(16, 64) ++
  new WithInclusiveCache  ++
  new WithNBreakpoints(8) ++
  new WithNBigCores(1)    ++
  new WithBootROMFile("workspace/bootrom.img") ++
  new WithExtMemSize(0x380000000L) ++
  new WithNExtTopInterrupts(8) ++
  new WithDTS("freechips,rocketchip-vivado", Nil) ++
  new WithDebugSBA ++
  new WithEdgeDataBits(64) ++
  new WithCoherentBusTopology ++
  new WithoutTLMonitors ++
  new BaseConfig)
\end{lstlisting}

Key components of this configuration include:
\begin{itemize}
    \item \texttt{WithNBigCores(1)}: Instantiates a single, high-performance 64-bit Rocket Core.
    \item \texttt{WithGemmini(16, 64)}: This is the crucial trait that integrates the Gemmini accelerator. It specifies a 16x16 systolic array mesh and a 64-bit wide DMA bus.
    \item \texttt{WithInclusiveCache}: Adds a last-level inclusive cache to the memory hierarchy, improving performance by reducing off-chip memory accesses.
    \item \texttt{WithExtMemSize(0x380000000L)}: Configures the size of the external DRAM (14 GiB in this case), which is essential for running a full operating system like Linux.
    \item \texttt{WithBootROMFile(...)}: Specifies the path to the boot ROM image that the processor will execute on reset.
\end{itemize}

\section{Gemmini Integration via RoCC}
The Gemmini accelerator is tightly integrated with the Rocket Core pipeline through the Rocket Custom Coprocessor (RoCC) interface. This interface allows custom instructions, defined in the RISC-V ISA, to be dispatched from the core to a coprocessor.

The integration is achieved through the \texttt{WithGemmini} configuration trait, which leverages the \texttt{BuildRoCC} mechanism provided by Rocket Chip. The code in Listing \ref{lst:withgemmini} shows how Gemmini is instantiated as a \texttt{LazyModule} and added to the list of RoCCs to be built.

\begin{lstlisting}[language=Scala, caption={The \texttt{WithGemmini} configuration trait.}, label=lst:withgemmini]
class WithGemmini(mesh_size: Int, bus_bits: Int) extends Config((site, here, up) => {
  case BuildRoCC => up(BuildRoCC) ++ Seq(
    (p: Parameters) => {
      implicit val q = p
      implicit val v = implicitly[ValName]
      LazyModule(new gemmini.Gemmini(gemmini.GemminiConfigs.defaultConfig.copy(
        meshRows = mesh_size, meshColumns = mesh_size, dma_buswidth = bus_bits)))
    }
  )
  case SystemBusKey => up(SystemBusKey).copy(beatBytes = bus_bits/8)
})
\end{lstlisting}

The Gemmini accelerator reserves a block of custom instruction opcodes. As defined in its configuration (\texttt{GemminiArrayConfig}), it uses \texttt{OpcodeSet.custom3}. When the Rocket Core's instruction decoder encounters an opcode from this set, it recognizes it as a RoCC instruction and dispatches it to the Gemmini unit, along with values from the processor's register file. The Rocket Tile then wires up the RoCC command and response channels between the core and the Gemmini module, enabling them to communicate.

\section{Development Environment}
The project requires a specific development environment to ensure that all tools, compilers, and dependencies are correctly configured. The primary environment is an Ubuntu 20.04 LTS workstation. The initial setup is automated by the \texttt{Makefile} through the `apt-install` target, which installs essential packages such as a Java Development Kit, device-tree-compiler, and the GCC toolchain for RISC-V.

The complete project, including all submodules for the RISC-V ecosystem components (Chipyard, U-Boot, Linux, OpenSBI), is checked out from the repository. The command `make update-submodules` ensures that all components are at the correct versions required for the build.


\section{Software Stack and Build Process}
To run a complete operating system and user applications, a comprehensive software stack is required. This project utilizes a standard boot flow for embedded Linux systems and automates the entire build process with a \texttt{Makefile}.

\subsection{Boot Flow: OpenSBI, U-Boot, and Linux}
The system boots in several stages:
\begin{enumerate}
    \item \textbf{Boot ROM}: On power-up, the Rocket Core begins execution from an on-chip Boot ROM. This initial code is responsible for basic hardware initialization and loading the next boot stage from an external device, in this case, an SD card.
    \item \textbf{OpenSBI}: The first piece of software loaded from the SD card is the RISC-V Open Source Supervisor Binary Interface (OpenSBI). OpenSBI provides a crucial abstraction layer, handling low-level hardware control (like inter-processor interrupts and timers) so that the operating system kernel doesn't need to be machine-specific.
    \item \textbf{U-Boot}: OpenSBI then loads and jumps to the Das U-Boot bootloader. U-Boot is a more powerful bootloader responsible for further hardware initialization (e.g., DDR memory) and loading the Linux kernel into RAM.
    \item \textbf{Linux Kernel}: Finally, U-Boot passes control to the Linux kernel. The kernel boots, mounts the root filesystem from the SD card, and starts the user-space services, providing a full Debian environment.
\end{enumerate}

\section{The Automated Build System}
The entire implementation, from hardware generation to a bootable Linux image, is orchestrated by a comprehensive \texttt{Makefile}. This build system automates hundreds of steps, ensuring a repeatable and reliable process. The primary command to build the entire system for the target hardware is:
\begin{verbatim}
make CONFIG=rocket64b1gem16 BOARD=vc707 bitstream
\end{verbatim}

\subsection{SoC Hardware Generation}
The first stage of the build process is to generate the Verilog HDL for the SoC. This is a multi-step process managed by the \texttt{Makefile}:
\begin{enumerate}
    \item \textbf{Initial Verilog and Device Tree Generation}: The build system invokes the Scala Build Tool (SBT) to compile the Chisel sources using the \texttt{Rocket64b1gem16} configuration. This generates the initial Verilog HDL and a base Device Tree Source (\texttt{.dts}) file, which describes the core SoC components as inferred by Chipyard's diplomacy framework, as described in Chapter 6.
    \item \textbf{Peripheral Integration}: This generated core is then integrated with several pre-existing, open-source peripheral controllers written in Verilog. These include the AXI UART controller (from the `uart` directory), the AXI SD Card controller (`sdc` directory), and the AXI Ethernet controller (`ethernet` directory), which is based on the Alex Forencich `verilog-ethernet` project.

    \item \textbf{Device Tree Customization}: A crucial step is the creation of the final device tree. The base \texttt{system.dts} is combined with a board-specific overlay, \texttt{board/vc707/bootrom.dts}, which defines the VC707's unique peripherals like the UART, MMC, and Ethernet controllers at their specific memory-mapped addresses. The \texttt{Makefile} then uses `sed` commands to patch this combined file with the correct runtime parameters, such as the main memory size (\texttt{0x40000000}) and the SoC's clock frequency (31.25 MHz for this configuration).
    \item \textbf{Boot ROM Generation}: The customized device tree is then passed to the boot ROM's own build system. The command `make -C bootrom ... bootrom.img` compiles the C code for the first-stage bootloader and embeds the compiled device tree binary within the final `bootrom.img` file.
    \item \textbf{Final HDL Generation}: With the finalized `bootrom.img` created, SBT is invoked a second time. This run uses the new boot ROM image to produce the final, correct Verilog HDL for the SoC, ensuring the processor's memory map includes the fully configured boot ROM.
\end{enumerate}

\subsection{Software Stack Compilation}
With the hardware defined, the \texttt{Makefile} proceeds to build the software stack using a cross-compiler toolchain specified by the `CROSS\_COMPILE\_LINUX` variable.
\begin{itemize}
    \item \textbf{Patching}: Before compilation, the build system applies project-specific patches to the Linux kernel and U-Boot source trees. This is handled by targets like `workspace/patch-linux-done`, which apply files from the `patches/` directory to add custom drivers or modify configurations.
    \item \textbf{U-Boot}: The `u-boot` target builds `u-boot-nodtb.bin`, a version of U-Boot without an embedded device tree, as it will be provided by OpenSBI.
    \item \textbf{OpenSBI}: The OpenSBI firmware is compiled with the `FW\_PAYLOAD\_PATH` variable pointing to the just-built U-Boot binary. This creates the final second-stage bootloader, \texttt{fw\_payload.elf}, which packages OpenSBI and U-Boot together.
    \item \textbf{Linux Kernel}: The `linux` target builds the `Image` file, which is the compressed, bootable Linux kernel.
\end{itemize}

\section{FPGA Deployment and System Boot}
The final stage of the automated flow is synthesizing the Verilog and deploying the system to the VC707 board.
\begin{enumerate}
    \item \textbf{Vivado Project Generation}: The build system does not use a static Vivado project. Instead, it generates a Tcl script, \texttt{workspace/rocket64b1gem16/system-vc707.tcl}, which contains all the settings for the project, including the FPGA part number (`xc7vx485tffg1761-2`).
    \item \textbf{Bitstream Synthesis}: The \texttt{bitstream} target executes Vivado in batch mode, running the generated Tcl script to create a project, synthesize the Verilog, and run place-and-route to generate the final \texttt{riscv\_wrapper.bit} file.
    \item \textbf{SD Card Preparation}: A bootable SD card is created using the \texttt{./mk-sd-card} script. This partitions the card and copies over the \texttt{fw\_payload.elf}, the Linux `Image`, and a Debian root filesystem.
\end{enumerate}
Once the FPGA is programmed and the SD card is inserted, the system boots into a fully functional Debian environment.

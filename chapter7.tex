\chapter{SYSTEM IMPLEMENTATION AND TESTING}
\label{chap:implementation}

This chapter details the implementation of the \acrshort{riscv} \acrfull{soc} featuring a Gemmini accelerator. The preceding chapters have established the theoretical foundations of the \acrshort{riscv} \acrshort{isa}, the Chipyard framework, and the architectural principles of \acrshort{dnn} acceleration. We now transition from theory to practice, documenting the complete process from hardware configuration and generation to final system validation on an \acrshort{fpga} platform. This chapter will cover the specific \acrshort{soc} configuration, the integration of the Gemmini accelerator as a \acrfull{rocc}, the software stack required to boot a full \acrshort{linux} operating system, the automated build process, and finally, the verification of the complete system on a Xilinx \acrshort{vc707} \acrshort{fpga} board. This practical account serves as a tangible demonstration of the maturity of the open-source, full-stack design methodology adopted for this research.

\section{Hardware Implementation: SoC Configuration}
The foundation of our hardware design is the Chipyard \acrshort{soc} generation framework, which provides a flexible and powerful environment for constructing complex \acrshort{riscv} systems. The result of this process is a complete, \acrshort{linux}-capable \acrshort{soc}, whose top-level architecture is illustrated in Figure \ref{fig:rocket_soc}. This diagram encapsulates the full-stack integration central to this thesis, depicting the system from the processor core and accelerator down to the specific peripheral \acrshort{ip} cores and their connections to the physical hardware on the \acrshort{fpga} board.

\begin{figure}[h!]
  \centering
  \includegraphics[width=\textwidth]{VC707_ImplementedRocket.pdf}
  \caption{The implemented Rocket SoC with Gemmini on the VC707 FPGA board. The Rocket Core is connected to a 16x16 Gemmini systolic array, and various peripherals are integrated via AXI interfaces.}
  \label{fig:rocket_soc}
\end{figure}

At the heart of the system is the \texttt{RocketTile} (Figure \ref{fig:rocket_soc}), which contains the 64-bit \acrshort{riscv} \texttt{RocketCore} and its private L1 instruction and data caches. Tightly coupled to the processor pipeline, as discussed in Chapter \ref{chap:gemmini_overview}, is the \texttt{Gemmini \acrshort{rocc} Accelerator}. This integration via the \acrshort{rocc} interface allows for low-latency command dispatch from the \acrshort{cpu} to the accelerator, a critical feature for high-performance operation.

The \texttt{RocketTile} communicates with the rest of the system through the coherent \texttt{SystemBus}, which is implemented using the \texttt{TileLink} protocol. This bus serves as the main interconnect for all major subsystems. The memory hierarchy extends from the L1 caches to a unified L2 cache and finally to the off-chip DDR3 memory. To bridge the on-chip \texttt{TileLink} protocol with the industry-standard \texttt{AXI} protocol used by the external memory controller \acrshort{ip}, a \texttt{TileLink to \acrshort{axi4} bridge} is automatically instantiated by the framework. This demonstrates a practical aspect of modern \acrshort{soc} design where components with disparate interface standards are seamlessly integrated.

To create a fully functional, \acrshort{linux}-capable computing platform, a rich set of peripherals is integrated via the \texttt{PeripheryBus}. Similar to the memory interface, a \texttt{TL to AXI Slave bridge} connects the \texttt{TileLink} bus to a set of \texttt{AXI}-based peripheral controllers. These include an \texttt{AXI SD Card Controller} to enable booting from an SD card, a \texttt{UART} controller for console \acrshort{io}, and a complete \acrshort{ethernet} subsystem for network connectivity. These controller \acrshortpl{ip}, written in \texttt{Verilog}, are then wired to their corresponding physical counterparts on the \acrshort{vc707} board, such as the SD card tray and the RJ45 \acrshort{ethernet} port.

\subsection{The \texttt{Rocket64b1gem16jtag} Configuration}
\label{sec:rocket64b1gem16jtag_config}

The comprehensive architecture shown in (Figure \ref{fig:rocket_soc}) is not designed by hand in \texttt{Verilog}, but is programmatically generated from a high-level \texttt{Scala} configuration. As outlined in Chapter \ref{chap:SingleCoreGemminiRiscVSystem}, this generator-based approach allows for rapid architectural exploration and ensures design consistency.

The specific configuration for our \acrshort{soc} is named \texttt{Rocket64b1gem16jtag}. This name concisely describes its key features: a 64-bit Rocket Core (\texttt{Rocket64}), one "big" core (\texttt{b1}), and a 16x16 Gemmini systolic array (\texttt{gem16}). This configuration is defined in \texttt{Scala} using Chipyard's \texttt{Config} classes, which employ a \texttt{mixin-based} approach to compose system components. This powerful paradigm allows features to be incrementally added to a base configuration through a series of traits, each beginning with the \texttt{With...} prefix. The core of the configuration is shown in Listing \ref{lst:Rocket64b1gem16jtag_config}.

\begin{lstlisting}[language=scala, caption={The \texttt{Rocket64b1gem16jtag} configuration class.}, label=lst:Rocket64b1gem16jtag_config]
class Rocket64b1gem16jtag extends Config(
  new WithGemmini(16, 64) ++
  new WithInclusiveCache  ++
  new WithNBreakpoints(8) ++
  new WithNBigCores(1)    ++
  new WithBootROMFile("workspace/bootrom.img") ++
  new WithExtMemSize(0x380000000L) ++
  new WithNExtTopInterrupts(8) ++
  new WithDTS("freechips,rocketchip-vivado", Nil) ++
  new WithDebugSBA        ++
  new WithJtagDTM         ++
  new WithEdgeDataBits(64) ++
  new WithCoherentBusTopology ++
  new WithoutTLMonitors ++
  new BaseConfig)
\end{lstlisting}

The \texttt{WithGemmini(16, 64)} trait is the most critical for this work. It instructs the generator to instantiate the Gemmini accelerator with a specific set of hardware parameters derived from the defaultConfig within the Gemmini generator source code. The generated accelerator is a sophisticated system in its own right, comprising several key hardware blocks:

\begin{itemize}
    \item \texttt{WithNBigCores(1)}: Instantiates a single, high-performance 64-bit Rocket Core. The Rocket Core was selected for its maturity and stability within the open-source ecosystem, providing a reliable foundation for our system.
    \item \texttt{WithGemmini(16, 64)}: This is the crucial trait that integrates the Gemmini \acrshort{dnn} accelerator, specifying a 16x16 systolic array mesh and a 64-bit wide \acrshort{dma} bus. This trait instructs the generator to instantiate a complete accelerator system based on its internal \texttt{defaultConfig}. The resulting hardware is a sophisticated system-within-a-system, visualized in Figure \ref{fig:gemmini_configuration_on_soc}, comprising:
      \begin{itemize}
        \item \textbf{A Systolic Array Core}: A 16x16 grid of \acrfullpl{pe}, each capable of an 8-bit integer multiply and a 32-bit integer accumulate per cycle. The array supports both \acrfull{ws} and \acrfull{os} dataflows.
        \item \textbf{An On-Chip Memory System}: A 256KB, 4-banked scratchpad memory for staging data and a separate 64KB, dual-ported accumulator memory for partial sums.
        \item \textbf{Control and Execution Logic}: A Reservation Station to enable out-of-order execution of primitive commands, managed by decoupled Load, Store, and Execute controllers.
        \item \textbf{Specialized Hardware Units}: A hardware Im2Col unit to accelerate convolution preprocessing and a 4-entry \acrfull{tlb} to support virtual memory.
      \end{itemize}
    \item \texttt{WithInclusiveCache}: Adds a last-level inclusive L2 cache to the memory hierarchy. This component is vital for performance, serving as a large, shared buffer that reduces the frequency of costly off-chip memory accesses, thereby helping to mitigate the "memory wall" problem.
    \item \texttt{WithExtMemSize(0x380000000L)}: Configures the size of the external \acrshort{dram} to 14 GiB. A large main memory is essential for running a full operating system like \acrshort{debian} \acrshort{linux}, which requires significant space for the kernel, user-space applications, and runtime data.
    \item \texttt{WithBootROMFile(...)}: Specifies the path to the boot \acrshort{rom} image. This \acrshort{rom} contains the first-stage bootloader code that the processor will execute on reset, initiating the system boot sequence.
\end{itemize}

This \acrshort{scala} configuration is then consumed by the Chipyard generator-based framework to produce the concrete hardware implementation. The resulting top-level architecture of the \acrshort{soc}, as deployed on the Xilinx \acrshort{vc707} \acrshort{fpga}, is illustrated in Figure \ref{fig:rocket_soc}.

\subsection{Accelerator Instantiation via the RoCC Interface}

The primary mechanism for integrating a tightly-coupled accelerator in Chipyard is through the \acrshort{rocc} interface, as described in Section \ref{subsec:rocc_interface}. In our design, this is achieved by using the \texttt{WithGemmini} configuration trait, shown in Listing~\ref{lst:withgemmini}. This class instructs the Chipyard generator to perform two critical actions: first, to instantiate the Gemmini accelerator as a \texttt{LazyModule}, and second, to connect it as a \acrshort{rocc} device.

\begin{lstlisting}[language=scala, caption={The \texttt{WithGemmini} configuration trait, which instantiates the accelerator as a \acrshort{rocc} device.}, label=lst:withgemmini]
class WithGemmini(mesh_size: Int, bus_bits: Int) extends Config((site, here, up) => {
  case BuildRoCC => up(BuildRoCC) ++ Seq(
    (p: Parameters) => {
      implicit val q = p
      implicit val v = implicitly[ValName]
      LazyModule(new gemmini.Gemmini(gemmini.GemminiConfigs.defaultConfig.copy(
        meshRows = mesh_size, meshColumns = mesh_size, dma_buswidth = bus_bits)))
    }
  )
  case SystemBusKey => up(SystemBusKey).copy(beatBytes = bus_bits/8)
})
\end{lstlisting}

The practical consequence of applying this trait is that the generator assigns the Gemmini accelerator to a reserved block of custom instruction opcodes—specifically \texttt{OpcodeSet.custom3} (corresponds to the binary value \texttt{0b1111011}). As a result, when the Rocket Core's instruction decoder encounters an instruction from this opcode space, it does not execute it. Instead, it dispatches the entire instruction, including register operands, directly to the Gemmini unit over the dedicated \acrshort{rocc} command channel that is automatically wired by the framework's diplomacy system. This automated, configuration-driven process is what establishes the low-latency, co-designed link that is essential for the accelerator's performance.

\subsection{Hardware Configuration Parameters}

The \texttt{WithGemmini} trait not only attaches the accelerator but also passes key parameters that define its generated hardware. For the final \texttt{Rocket64b1gem16jtag} configuration, the following parameters were used, resulting in the architecture shown in Figure~\ref{fig:gemmini_configuration_on_soc}:
\begin{itemize}
    \item \textbf{Systolic Array Dimensions (\texttt{mesh\_size}):} A value of 16 was used, generating a 16$\times$16 grid of Processing Elements. This provides a total of 256 parallel MAC units.
    \item \textbf{DMA Bus Width (\texttt{bus\_bits}):} A value of 64 was used, matching the data width of the Rocket Core and providing a 64-bit wide data path to the system bus.
    \item \textbf{On-Chip Memory:} The default configuration was used, which instantiates a 256KB, 4-banked scratchpad for staging data, and a separate 64KB, dual-ported accumulator memory for storing partial sums.
\end{itemize}
These parameters represent a specific design point, balancing high computational throughput with the resource constraints of the target FPGA.

\section{Peripheral Integration}

To create a fully functional, \acrshort{linux}-capable computing platform, the core \acrshort{soc} must be integrated with a rich set of \acrshort{io} peripherals for storage, networking, and user interaction. This section details the architecture and integration of these essential components. Unlike the \acrshort{chisel}-generated processor core which uses the \texttt{TileLink} protocol, most peripherals are integrated as pre-existing, open-source Verilog \acrshort{ip} blocks that use the industry-standard \acrshort{axi4} protocol.

This creates a heterogeneous bus environment, which is managed by the Chipyard framework's diplomacy-generated protocol bridges. As shown in the overall system diagram (Figure \ref{fig:rocket_soc}), peripherals are not attached to the main coherent \texttt{SystemBus}. Instead, they connect to a dedicated, \acrshort{axi4}-based \texttt{PeripheryBus}. A specialized \textbf{TileLink to \acrshort{axi4} Bridge} is automatically instantiated by the framework to handle all communication between the \acrshort{cpu} and this peripheral bus, managing protocol translation, address decoding, and data width conversion.

Each peripheral is managed by a dedicated controller \acrshort{ip} that acts as a middleman, translating high-level AXI bus transactions from the Rocket Core into the specific low-level protocols required by the hardware (e.g., SD command sequences or \acrshort{ethernet} \acrshort{mac} framing). For the system software to utilize these components, a corresponding driver must be present in the operating system. This driver interacts with the controller's memory-mapped registers to initiate data transfers and handle interrupts. The following subsections will briefly describe the implementation of the key peripherals integrated into this design: the SD Card controller, the \acrshort{uart} controller, and the \acrshort{ethernet} subsystem, among others.

\subsection{DDR Memory: High-Bandwidth Main Memory}

The \acrshort{soc}'s main memory system is built around a high-performance DDR3 SDRAM interface, which is essential for providing the capacity and bandwidth required to run a full \acrshort{linux} operating system and handle the large data sets of \acrshort{dnn} workloads. The implementation does not use a custom controller but instead leverages the industry-standard \textbf{Xilinx \acrfull{mig} 7-Series \acrshort{ip} core}. This is a common and robust design practice that ensures reliable, high-frequency memory operation.

A key architectural feature of this design is its scalability. While the processor and system bus are designed with a \textbf{34-bit address width, capable of accessing up to 16 GiB of memory}, the current physical implementation on the \acrshort{vc707} board uses a 1 GiB SODIMM. The AXI SmartConnect bridge, instantiated by Chipyard, automatically handles the address translation between the large logical address space and the smaller physical memory map. This demonstrates a forward-looking design, allowing for future memory expansion with minimal changes to the core \acrshort{soc} architecture.

\subsection{SD Card: AXI SD Card Controller and SD Mode}
The \acrshort{soc} includes an AXI SD Card controller, which allows the system to boot from an SD card. This controller is integrated into the system using the Chipyard framework's diplomacy mechanism, which automatically wires up the necessary AXI interfaces.

The SD card is accessed in SD mode, which is a common mode for embedded systems. The controller supports standard SD commands and allows the system to read and write data blocks, making it suitable for booting the operating system and storing user data.

\subsection{UART: AXI UART Controller}

To provide essential console \acrshort{io} for debugging and user interaction with the operating system, the \acrshort{soc} integrates a robust \acrshort{uart} controller. This component is not a generic library \acrshort{ip} but a custom-designed Verilog module tailored for this system, demonstrating the ability to integrate bespoke hardware into the Chipyard flow.

The controller is connected to the \texttt{PeripheryBus} via an \acrshort{axi4}-Lite interface, making it a memory-mapped peripheral accessible by the Rocket Core. Architecturally, it is designed for high-performance, reliable communication and includes several key hardware features:
\begin{itemize}
    \item \textbf{\acrshort{fifo} Buffering:} The controller features independent 16-entry transmit (TX) and receive (RX) \acrshortpl{fifo}. These hardware buffers are crucial for preventing data loss at high baud rates, as they decouple the \acrshort{cpu} from the byte-by-byte management of the serial link by allowing it to read and write data in bursts.
    \item \textbf{Hardware Flow Control:} Full \acrshort{rts}/\acrshort{cts} hardware flow control is implemented, allowing the \acrshort{uart} to automatically signal its readiness to receive data and to pause transmission if the remote device is not ready. This is essential for preventing buffer overruns in high-throughput scenarios.
    \item \textbf{Interrupt Generation:} The controller can generate interrupts to the \acrshort{cpu} based on configurable events, such as the receive \acrshort{fifo} reaching a certain threshold. This enables efficient, interrupt-driven \acrshort{io} handling in the \acrshort{linux} kernel, rather than relying on inefficient polling.
\end{itemize}

\subsection{Ethernet: AXI Ethernet Controller}

The \acrshort{ethernet} subsystem provides high-speed network connectivity for the \acrshort{riscv} RocketChip \acrshort{soc}, enabling communication with external systems and networks. The implementation consists of a four-layer architecture that bridges the processor's \acrshort{axi4} bus interface to the physical \acrshort{ethernet} connection on the \acrshort{vc707} \acrshort{fpga} board.

The \acrshort{ethernet} subsystem is implemented as a hierarchical design with four distinct functional blocks, as illustrated in Figure \ref{fig:rocket_soc}. 

\begin{enumerate}
  \item \textbf{Ethernet \acrshort{dma} Controller}: serves as the primary interface between the RocketChip \acrshort{soc} and the \acrshort{ethernet} \acrshort{mac} layer. It provides functionality for managing data transfers between the \acrshort{soc} and the \acrshort{ethernet} \acrshort{mac}, including packet buffering, flow control, and interrupt handling.

  \item \textbf{\acrshort{sgmii} 1Gbps \acrshort{ethernet} MAC}: The \acrshort{mac} (Media Access Control) layer is implemented using the open-source \texttt{eth\_mac\_1g\_fifo} module from the verilog-ethernet project \cite{verilog-ethernet}. This component provides: \acrshort{ieee} 802.3 Compliance, integrated frame-level \acrshort{fifo} Buffering, Frame Processing (Automatic frame padding, FCS generation and checking, and frame validation), \acrshort{axi4}-Stream Interface, Standard GMII Interface (Gigabit Media Independent Interface).

  \item \textbf{\acrshort{sgmii} PHY Interface}: implemented using Xilinx's integrated \acrshort{sgmii} \acrshort{ip} core within the \acrshort{vc707} \acrshort{fpga}. This layer provides: \acrshort{sgmii} Protocol (\acrlong{sgmii}), Auto-negotiation, Clock Generation (125 \acrshort{mhz} clock), Signal Conditioning.

  \item \textbf{Physical RJ45 Interface}: The physical layer terminates at the RJ45 connector on the \acrshort{vc707} board.
\end{enumerate}

\subsection{System Monitoring: XADC and Fan Control}

To ensure operational stability and manage thermal output, the \acrshort{soc} integrates a dedicated system monitoring and fan control subsystem. This demonstrates a hybrid design approach, combining vendor \acrshort{ip} with custom control logic for a robust, real-world solution. The subsystem consists of two primary components:

\begin{itemize}
    \item \textbf{Xilinx \acrshort{xadc} \acrshort{ip} Core:} The on-chip \acrfull{xadc} is used for real-time monitoring of the \acrshort{fpga}'s internal temperature and critical supply voltages (VCCINT, VCCAUX). This \acrshort{ip} is configured to operate in a continuous sampling mode and is connected to the system via an \acrshort{axi4}-Lite interface.
    
    \item \textbf{Custom Fan Controller:} A custom-designed Verilog module provides \acrshort{pwm}-based control for the chassis fan. Crucially, this module is directly connected to the \acrshort{xadc}'s hardware thermal alarm pin. This creates an autonomous, hardware-based safety mechanism: if the die temperature exceeds a predefined threshold (e.g., 60°C), the alarm triggers an emergency override, forcing the fan to 100\% duty cycle, independent of any software control.
\end{itemize}

\section{Software Stack and Build Process}
To run a complete operating system and user applications, a comprehensive software stack is required. This project utilizes a standard boot flow for embedded \acrshort{linux} systems.

\subsection{Boot Flow: OpenSBI, U-Boot, and Linux}
The system boots in several stages:
\begin{enumerate}
    \item \textbf{Boot ROM}: On power-up, the Rocket Core begins execution from an on-chip Boot \acrshort{rom}. This initial code is responsible for basic hardware initialization and loading the next boot stage from an external device, in this case, an SD card.
    \item \textbf{OpenSBI}: The first piece of software loaded from the SD card is the \acrfull{opensbi} \cite{opensbi_project}. \acrshort{opensbi} provides a crucial abstraction layer, handling low-level hardware control (like inter-processor interrupts and timers) so that the operating system kernel doesn't need to be machine-specific.
    \item \textbf{U-Boot}: \acrshort{opensbi} then loads and jumps to the Das U-Boot bootloader. U-Boot is a more powerful bootloader responsible for further hardware initialization (e.g., \acrshort{ddr} memory) and loading the \acrshort{linux} kernel into \acrshort{ram}.
    \item \textbf{\acrshort{linux} Kernel}: Finally, U-Boot passes control to the \acrshort{linux} kernel. The kernel boots, mounts the root filesystem from the SD card, and starts the user-space services, providing a full \acrshort{debian} environment.
\end{enumerate}

\subsection{SoC Hardware Generation}
The first stage of the build process is to generate the Verilog \acrshort{hdl} for the \acrshort{soc}. 
\begin{enumerate}
    \item \textbf{Initial Verilog and Device Tree Generation}: The build system invokes the \acrshort{scala} Build Tool (SBT) to compile the \acrshort{chisel} sources using the \texttt{Rocket\allowbreak 64b1gem16jtag} configuration. This generates the initial Verilog \acrshort{hdl} and a base Device Tree Source (\texttt{.dts}) file, which describes the core \acrshort{soc} components as inferred by Chipyard's diplomacy framework, as described in Chapter 6.
    \item \textbf{Peripheral Integration}: This generated core is then integrated with several pre-existing, open-source peripheral controllers written in Verilog. These include the AXI \acrshort{uart} controller, the AXI SD Card controller, and the AXI \acrshort{ethernet} controller.
    \item \textbf{Device Tree Customization}: A crucial step is the creation of the final device tree. The base \texttt{system.dts} is combined with a board-specific overlay, \texttt{board/vc707/bootrom.dts}, which defines the \acrshort{vc707}'s unique peripherals like the \acrshort{uart}, MMC, and \acrshort{ethernet} controllers at their specific memory-mapped addresses.
    \item \textbf{Boot \acrshort{rom} Generation}: The customized device tree is then passed to the boot \acrshort{rom}'s own build system, which compiles the C code for the first-stage bootloader and embeds the compiled device tree binary within the final `bootrom.img` file.
    \item \textbf{Final \acrshort{hdl} Generation}: With the finalized `bootrom.img` created, SBT is invoked a second time. This run uses the new boot \acrshort{rom} image to produce the final, correct Verilog \acrshort{hdl} for the \acrshort{soc}, ensuring the processor's memory map includes the fully configured boot \acrshort{rom}.
\end{enumerate}

\section{Gemmini Testing}
We are going to use the gemmini-rocc-tests (https://github.com/ucb-bar/gemmini-rocc-tests) to test the Gemmini accelerator. The tests are designed to verify the functionality of the Gemmini \acrshort{rocc} interface and the correctness of the accelerator's operations. The tests cover a wide range of scenarios, including basic arithmetic operations, matrix multiplication, convolution, and more complex \acrshort{dnn} workloads.

With the hardware and software stack fully implemented and the testing methodology defined, the system is now ready for validation and evaluation. The following chapter presents the culminating results of this work, analyzing the hardware resource utilization of the final design, validating the full-stack software deployment, and, most critically, quantifying the performance impact of the Gemmini accelerator.

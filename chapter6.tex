\chapter{Gemmini's Internal Architecture and Programming Model}
\label{chap:gemmini_internals}

While Chapter \ref{chap:gemmini_overview} described the conceptual architecture of Gemmini, this chapter explores its internal structure and the software interfaces used to control it. This analysis will follow the journey of a single instruction from the host CPU down to the physical hardware, revealing how Gemmini's sophisticated design translates high-level commands into high-performance computation. A deeper understanding of these implementation-level details is necessary to effectively program the accelerator and analyze its performance.

\section{The Command-Unrolling Hierarchy}
\label{sec:command_unrolling}

A custom \texttt{RoCC} instruction sent from the Rocket core is not executed directly by the systolic array. Instead, it triggers a complex sequence of events within the Gemmini accelerator's internal controller modules. The overall structure of the generated hardware, is shown in Figure~\ref{fig:gemmini_internal_modules}. This section details the key components of this internal pipeline.


\subsection{Command Unrolling and Buffering for Decoupled Execution via LoopConv and LoopMatmul}

This hardware-based command unrolling is a defining characteristic of a powerful, tightly-integrated co-processor. This design offloads what would otherwise be thousands of CPU instructions—for loop control, address calculation, data dependency checking, and synchronization—into a single accelerator command. By handling this complexity autonomously within its own hardware controllers, Gemmini frees the Rocket Core to perform other tasks, demonstrating a highly efficient division of labor between the general-purpose CPU and the specialized accelerator.

The stream of micro-operations unrolled by the high-level controllers is not fed into a rigid, lock-step pipeline. Instead, Gemmini employs a more sophisticated and powerful paradigm: decoupled execution managed by a set of independent, communicating Finite State Machines (FSMs). This design allows the various stages of a complex operation—loading data, executing computation, and storing results—to proceed concurrently and asynchronously, maximizing hardware utilization.

The initial \texttt{RoCC} instructions received from the CPU are often "complex" commands that encapsulate entire loops (e.g., `loop\_matmul`). As shown in Figure~\ref{fig:command_unrollers}, modules like \texttt{LoopMatmul} and \texttt{LoopConv} are responsible for unrolling these high-level tasks into a stream of simpler, primitive micro-operations for loading, storing, and executing on tiled sub-matrices. These primitive commands are then buffered in a queue before being sent to a central dispatcher.

Due to convolution operations inherently require two levels of decomposition to be efficiently executed on the systolic array hardware, the interface between \texttt{LoopConv} and \texttt{LoopMatmul} reflects a fundamental architectural principle: hierarchical loop unrolling. 

Once a \texttt{RoCCCommand} crosses the interface into Gemmini, it is not executed directly by the systolic array. Instead, the CPU often issues high-level, almost CISC-like commands such as \texttt{LOOP\_WS} or \texttt{LOOP\_CONV\_WS}, which encapsulate entire, complex operations. These commands are received by dedicated hardware controllers — \texttt{LoopMatmul} and \texttt{LoopConv} — which act as micro-code engines. Their primary function is to interpret these high-level instructions and "unroll" them into a sequence of simpler, primitive micro-operations that can be dispatched to the underlying hardware units.

At the first level, \texttt{LoopConv} decomposes high-level convolution operations into a sequence of matrix multiplication primitives. This transformation handles the complex six-dimensional loop structure inherent in convolutions, including batch dimensions, input/output channels, and spatial dimensions. At the second level, \texttt{LoopMatmul} further breaks down these matrix multiplication operations into smaller tiles that can be efficiently processed by the systolic array's fixed dimensions.

This hierarchical approach ensures that the complex nested loop structures of convolution operations are systematically reduced to primitive operations that can be directly executed by the underlying hardware. The \texttt{LoopMatmul} module thus acts as an intermediary controller, translating matrix-level operations into the tile-based computations required by the systolic array architecture.

\subsubsection{LoopConv}

\begin{figure}[htbp]
    \centering
    \includegraphics[width=\textwidth]{Gemmini_Internal_LoopConv.pdf}
    \caption{LoopConv module}
    \label{fig:loop_conv}
\end{figure}

The LoopConv block is a \textbf{Convolution Loop Unroller}, or in other words, it is the High-Level Command Unrolling module within the Gemmini systolic array accelerator. Usually, convolution operations involve complex nested loops over: Batch dimensions (N), Input/Output channels (C), Spatial dimensions (H, W), and Kernel dimensions (R, S). Without LoopConv, programmers would need to manually implement these 6-7 nested loops, handle data tiling, and manage resource allocation. LoopConv provides a single high-level instruction (for example, \texttt{gemmini\_loop\_conv\_ws} or \texttt{gemmini\_loop\_ws} in C code, ...) that can perform entire convolution operations automatically. 

The internal architecture of the \texttt{LoopConv} controller, depicted in Figure \ref{fig:loop_conv}, provides a clear illustration of this command unrolling process. As the figure shows, a single high-level convolution command is not executed serially. Instead, it triggers three independent, parallel load units to begin fetching the necessary tensors concurrently.

\begin{itemize}
    \item \textbf{\texttt{LoopConvLdInput}}: Loads input feature maps from memory.
    \item \textbf{\texttt{LoopConvLdWeight}}: Loads convolution kernel weights from memory.
    \item \textbf{\texttt{LoopConvLdBias}}: Loads bias values from memory.
\end{itemize}

After the loaded data is fully received, it begins the execution phase.

\begin{itemize}
    \item \textbf{\texttt{LoopConvExecute}}: Executes the convolution operation.
    \item \textbf{\texttt{Arbiter}}: A 5-to-1 arbiter that manages access to the memory interface, ensuring that the three load units and the execute unit do not contend for the same resources simultaneously.
\end{itemize}

\subsubsection{LoopMatmul}

\begin{figure}[htbp]
    \centering
    \includegraphics[width=\textwidth]{Gemmini_Internal_LoopMatmul.pdf}
    \caption{LoopMatmul module}
    \label{fig:loop_matmul}
\end{figure}

The \texttt{LoopMatmul} module serves as the matrix multiplication command unroller within the Gemmini architecture. It receives commands from the \texttt{LoopConv} module and processes five distinct types of operations:

\begin{itemize}
    \item \textbf{LOAD3\_CMD (MVIN)}: Loads data from DRAM to scratchpad memory
    \item \textbf{STORE\_CMD (MVOUT)}: Stores data from scratchpad memory to DRAM
    \item \textbf{PRELOAD\_CMD}: Preloads weights into the systolic array
    \item \textbf{COMPUTE\_CMD}: Executes matrix multiplication operations
    \item \textbf{CONFIG\_CMD}: Configures the load/store/execute pipeline parameters
\end{itemize}

The internal structure of the \texttt{LoopMatmul} controller exemplifies this architecture. It is composed of several independent hardware modules:
\begin{itemize}
    \item \textbf{\texttt{LoopMatmulLdA}}: Loads matrix A from DRAM to scratchpad memory
    \item \textbf{\texttt{LoopMatmulLdB}}: Loads matrix B (weights) from DRAM to scratchpad memory
    \item \textbf{\texttt{LoopMatmulLdD}}: Loads bias/accumulator data from DRAM to accumulator memory
    \item \textbf{\texttt{LoopMatmulExecute}}: Performs the actual matrix multiplication computation
    \item \textbf{\texttt{LoopMatmulStC}}: Stores results from accumulator back to DRAM
    \item \textbf{\texttt{LoopMatmulStCSpad}}: Stores results from accumulator to scratchpad memory
\end{itemize}

While these modules operate independently, they are coordinated through a lightweight handshake mechanism referred to in the design as iterator synchronization. For instance, the \texttt{LoopMatmulExecute} will not begin computation on a tile of data until it receives a signal that the \texttt{LoopMatmulLdA} and \texttt{LoopMatmulLdB} have successfully loaded the required operands into the scratchpad. This allows the \texttt{Load} modules to work ahead, fetching data for a future computation (\texttt{tile i+1}) while the \texttt{Execute} module is still busy processing the current one (\texttt{tile i}).

This decoupled architecture is a deliberate and critical design choice for overcoming the "memory wall". The high latency of fetching data from off-chip DRAM is a primary performance bottleneck in any accelerator. By overlapping the long-latency memory operations (Load and Store) with the core computation (Execute), the system effectively hides this latency. This ensures that the systolic array—the most valuable computational resource—is starved for data as infrequently as possible, maximizing its utilization and achieving a throughput that would be unattainable with a simple, rigid pipeline.

The Arbiter employs a fixed-priority scheduling policy to manage resource contention among the parallel execution units:

\begin{enumerate}
    \item \textbf{Highest Priority - Store to DRAM}: Commands from the \texttt{LoopMatmulStC} module receive top priority to prevent accumulator buffer overflow and maintain pipeline flow.
    \item \textbf{Execute Operations}: The \texttt{LoopMatmulExecute} module's preload and compute commands receive second priority to keep the systolic array actively computing.
    \item \textbf{Load Bias/Accumulator}: The \texttt{LoopMatmulLdD} module's commands for loading bias data receive third priority.
    \item \textbf{Load Input Matrices}: A weighted sub-arbiter manages requests from \texttt{LoopMatmulLdA} and \texttt{LoopMatmulLdB} modules with fourth priority.
    \item \textbf{Lowest Priority - Store to Scratchpad}: The \texttt{LoopMatmulStCSpad} module receives lowest priority as scratchpad stores are less critical than DRAM operations.
\end{enumerate}

This priority scheme ensures that result data is promptly written to DRAM to free accumulator resources, while maintaining sufficient data throughput to keep the computational units busy.

The impressive result, LoopMatmul transforms a single \texttt{LOOP\_WS(matmul 1024x1024)} command into \textbf{thousands} of precisely calculated, optimally ordered, resource-aware hardware operations ready for immediate execution by the controllers.

\subsection{Reservation Station and Execution Control}

LoopMatmul provides ReservationStation with:

\begin{itemize}
    \item \textbf{Optimally Sequenced Commands}: Thousands of individual operations from high-level matrix specifications
    \item \textbf{Complete Address Calculation}: DRAM offsets, scratchpad addresses, stride handling
    \item \textbf{Resource-Aware Flow Control}: Prevents overwhelming downstream controllers
    \item \textbf{Dependency Management}: Ensures proper ordering without explicit dependencies in ReservationStation
    \item \textbf{Concurrent Loop Support}: Enables double-buffering for maximum throughput
    \item \textbf{Attribution Metadata}: Marks commands for proper tracking and debugging
\end{itemize}

The ReservationStation receives commands from the LoopMatmul:
\begin{itemize}
    \item \textbf{LOAD\_CMD}: Load matrix A block (4x4) from DRAM to scratchpad
    \item \textbf{LOAD2\_CMD}: Load matrix B block (4x4) from DRAM to scratchpad
    \item \textbf{LOAD3\_CMD}: Load bias (4x4) from DRAM to accumulator
    \item \textbf{PRELOAD\_CMD}: Preload B matrix into systolic array
    \item \textbf{COMPUTE\_AND\_FLIP\_CMD}: Perform matrix multiplication A*B
    \item \textbf{STORE\_CMD}: Store result (4x4) from accumulator to DRAM
\end{itemize}

The stream of primitive commands is received by the ReservationStation module, which reorders and dispatches them to the appropriate back-end controllers: LoadController, StoreController and and ExecuteController. 

\begin{itemize}
    \item \textbf{LoadController}: Handles all data loading operations, fetching data from DRAM to the scratchpad memory.
    \item \textbf{StoreController}: Manages data storage operations, writing results from the scratchpad back to DRAM.
    \item \textbf{ExecuteController}: Manages the actual computation. It issues commands to the systolic array and orchestrates the movement of data between the scratchpad and the computational units. It also contains logic to manage optional units, such as the hardware \texttt{im2col} unit or data transposer (Figure~\ref{fig:execute_controller}). 
    \begin{itemize}
        \item \textbf{Im2Col Module}: Specialized SRAM controller for convolution operations that converts image data into column format for efficient convolution, manages sliding window operations over input data, handles address generation for accessing input feature maps, and provides specialized data access patterns for CNN operations.
        \item \textbf{Queue (sram\_read\_signals\_q)}: Pipeline synchronization buffer that buffers control signals for SRAM read operations, provides timing alignment between address generation and data availability, and handles pipeline delays in the Im2Col data path.
        \item \textbf{Queue (mesh\_cntl\_signals\_q)}: Mesh control signal buffer that queues control signals fed into the computational mesh, synchronizes computation control with data arrival timing, and provides pipeline buffering for mesh operations.
        \item \textbf{MultiHeadedQueue}: Multi-port queue for command buffering that allows multiple commands to be read simultaneously, provides flexible command scheduling and issue capabilities, and supports out-of-order execution patterns.
        \item \textbf{TransposePreloadUnroller}: Command transformation unit that unrolls complex operations into simpler primitive operations, handles matrix transpose operations for weight-stationary dataflow, and manages preload command sequences for optimal data placement.
        \item \textbf{MeshWithDelays (Computational Mesh)}: The main systolic array for matrix computations that performs actual matrix multiplication operations, implements systolic array dataflow (input/weight/output stationary), handles multiple simultaneous matrix multiplications, and manages timing and data flow through the PE array.
    \end{itemize}
\end{itemize}

\subsection{Scratchpad: the Local Memory Subsystem}

The Scratchpad (Figure~\ref{fig:scratchpad_module}) implements the on-chip memory, containing the SRAM banks and logic for interfacing with the DMA engine and the systolic array's accumulator. It serves as the central data hub of the matrix multiplication accelerator, acting as a high-speed, local memory subsystem that bridges the gap between external DRAM and the compute units. 

Far more than simple storage, the Scratchpad implements a sophisticated data movement engine with integrated processing capabilities, dual data paths, and complex arbitration logic, enabling the high-throughput, low-latency data access patterns essential for efficient matrix computation. Its design demonstrates the critical importance of specialized memory subsystems in achieving peak performance in domain-specific accelerators.

The Scratchpad sits at the heart of the Gemmini data flow architecture. There's two primary interfaces that the Scratchpad exposes to work with the rest of the system:
\begin{itemize}
    \item \textbf{External Memory Interface}: Via TileLink and DMA for bulk data transfers with DRAM
    \item \textbf{Compute Unit Interface}: Direct access for the systolic array and accumulator units
\end{itemize}

The Scratchpad's internal architecture reveals its complexity as a data processing subsystem rather than passive storage. The key components include:

\begin{itemize}
    \item \textbf{Memory Banks}: 
    \begin{itemize}
        \item \texttt{ScratchpadBank (spad\_mems\_*)}: Multiple SRAM banks storing input data (weights, activations) for the systolic array, enabling parallel access patterns
        \item \texttt{AccumulatorMem (acc\_mems\_*)}: Specialized banks storing partial sums and accumulation results, with integrated support for activation functions and scaling operations
    \end{itemize}
    
    \item \textbf{DMA Engines}: \texttt{StreamReader} and \texttt{StreamWriter} for data transfers between external memory and internal banks
    
    \item \textbf{Integrated Data Processing Units}: Built-in data transformation units to reduce CPU overhead
    \begin{itemize}
        \item \texttt{VectorScalarMultiplier (vsm/vsm\_1)}: Applies scaling operations to data during movement, with separate scalers for scratchpad and accumulator data paths
        \item \texttt{PixelRepeater}: Handles pixel repetition optimizations for first-layer convolution operations
        \item \texttt{AccumulatorScale unit (acc\_scale\_unit)}: Critical component applying scaling and activation functions to accumulator data before memory writes
        \item \texttt{Normalizer unit (acc\_norm\_unit)}: Performs normalization operations on accumulator data
        \item \texttt{ZeroWriter}: Generates zero data when the \texttt{all\_zeros} flag is set, avoiding unnecessary memory reads
    \end{itemize}
    
    \item \textbf{Pipeline Infrastructure}: Built with multiple queue stages to ensure smooth data flow and prevent pipeline stalls.
    
\end{itemize}

\section{The RoCC Interface that controls Gemmini}
\label{sec:gemmini_rocc_interface}

The Gemmini accelerator is controlled through a custom \texttt{RoCC} interface, which allows the Rocket Core to issue commands and receive results. This interface is designed to be flexible and efficient, enabling high-throughput data transfers and command execution.



\subsection{Resource Management and Arbitration}

The decoupled, parallel architecture described previously, while powerful, creates an inherent engineering challenge: contention for shared hardware resources. With multiple independent Load, Execute, and Store modules operating concurrently, they will inevitably attempt to access the same resources—such as the scratchpad memory ports or the primary DMA engine—at the same time. Gemmini addresses this challenge through a hierarchy of dedicated hardware arbiters.

These arbiters act as traffic controllers for internal data and command pathways. For instance, the \texttt{LoopConv} controller, as shown previously in Figure \ref{fig:loopconv_controller}, features a central 5-to-1 arbiter that serializes requests from the five parallel units before they are dispatched. The \texttt{LoopMatmul} controller employs an even more complex, two-stage arbitration scheme which includes a \texttt{Global 5-Way Arbiter}. This hardware explicitly enforces a fixed-priority policy, granting higher precedence to \texttt{Store} operations to free up internal result buffers, followed by \texttt{Execute} and \texttt{Load} operations. This ensures that the system does not deadlock and that resource access is allocated in a deterministic and efficient manner.

Beyond simply resolving simultaneous requests, the system must also manage its overall load to prevent its internal queues and buffers from overflowing. This is achieved through a feedback mechanism managed by resource utilization counters. These hardware counters track the number of load, store, and execute micro-operations currently in flight. If the number of pending commands in the Re-Order Buffer (ROB) exceeds a hardware-defined threshold, the controller asserts a backpressure signal (e.g., \texttt{rob\_overloaded}) to the upstream FSMs, temporarily stalling them from issuing new commands until resources become available.

The inclusion of explicit hardware for arbitration and backpressure-based flow control is a critical indicator of the design's sophistication. While a simplistic proof-of-concept accelerator might function correctly under ideal, low-load conditions, it would likely fail or deadlock under the high-throughput, concurrent scenarios that this system is designed for. Therefore, the presence of this robust resource management infrastructure proves the maturity of the Gemmini accelerator, demonstrating an architecture designed not just for theoretical correctness but for practical, high-performance operation.


\section{The Multi-Level Programming Model}
\label{sec:gemmini_programming_model}

To cater to different user needs, from application developers to hardware architects, Gemmini supports a multi-level programming model. This stack provides layers of abstraction, allowing users to work at a level appropriate for their task, from direct hardware control to high-level framework integration.

\subsection{Low-Level: Gemmini ISA}
At the lowest level, Gemmini is controlled by its custom RoCC instruction set. These instructions are typically wrapped in C preprocessor macros for easier use from C/C++ code. The instruction set includes primitive commands like \texttt{mvin} (move data in), \texttt{mvout} (move data out), \texttt{preload} (load data into the PE array), and \texttt{compute}. It also features more "complex" instructions like \texttt{loop\_matmul} that abstract away the manual tiling and scheduling of primitive commands, offloading the loop control to hardware state machines \cite{Genc2022GemminiMLSys}.

\subsection{Mid-Level: Hand-Tuned C Library}
To abstract the complexities of direct ISA programming, Gemmini provides a C library (typically accessed via \texttt{gemmini.h}). This library offers functions for common DNN operations, such as \texttt{tiled\_matmul} and \texttt{tiled\_conv}. These functions implement optimized heuristics for loop tiling and data movement to maximize scratchpad utilization based on the specific hardware parameters of the generated Gemmini instance.

\subsection{High-Level: Compiler Support (Conceptual)}
The Gemmini ecosystem is designed to support higher-level compilation flows. This involves tools that can take DNN models described in standard frameworks like ONNX (Open Neural Network Exchange) and compile them down to Gemmini instructions, either by calling the mid-level C library or by directly generating low-level ISA calls. This further simplifies the deployment of DNNs on Gemmini-accelerated SoCs.

\chapter{Gemmini's Internal Architecture and Programming Model}
\label{chap:gemmini_internals}

While Chapter \ref{chap:gemmini_overview} described the conceptual architecture of Gemmini, this chapter explores its internal structure and the software interfaces used to control it. This analysis will follow the journey of a single instruction from the host CPU down to the physical hardware, revealing how Gemmini's sophisticated design translates high-level commands into high-performance computation. A deeper understanding of these implementation-level details is necessary to effectively program the accelerator and analyze its performance.

\begin{figure}[htbp]
    \centering
    \includegraphics[width=\textwidth]{Gemmini_Internal_Overview.pdf}
    \caption{Overview of the internal modules in the generated Gemmini hardware architecture, showing the flow of commands from the RoCC interface through various queues and controllers.}
    \label{fig:gemmini_internal_modules}
\end{figure}

Figure~\ref{fig:gemmini_internal_modules} serves as a high-level architectural blueprint for the entire Gemmini accelerator. The journey of a command begins when a \texttt{RoCCCommand} is dispatched from the \texttt{RocketCore} and arrives at the \textbf{RoCC Interface}. The command first enters the \textbf{Command Processing} block, where it is enqueued before being passed to the \textbf{Loop Controllers}. Here, the two-level command-unrolling hierarchy (\texttt{LoopConv} and \texttt{LoopMatmul}) autonomously translates the high-level instruction into a stream of simpler, tiled micro-operations. These primitive commands are then staged in the \textbf{ReservationStation}, which acts as a central dispatch hub.

From the Reservation Station, commands are issued to the three independent \textbf{Execution Controllers}, which manage the core decoupled operations of the accelerator. The \texttt{LoadController} and \texttt{StoreController} orchestrate all data movement with the \textbf{Memory Subsystem}, issuing requests through its \texttt{TileLink Interface} to either the on-chip \texttt{spad} (Scratchpad) or off-chip DRAM. In parallel, the \texttt{ExecuteController} drives the \textbf{Compute Pipeline}, managing the optional \texttt{Im2Col} unit and issuing commands to the systolic \texttt{mesh} and the post-processing \texttt{accumulator \& scaler}. This entire process is supported by system-level services, such as the \textbf{FrontendTLB}, which handles virtual memory address translation via the \texttt{io.ptw} port.

This decoupled, multi-stage architecture is the key to Gemmini's performance, allowing long-latency memory operations to be overlapped with high-throughput computation. The subsequent sections will now explore each of these major blocks in detail.

\section{The Command-Unrolling Hierarchy}
\label{sec:command_unrolling}

A custom \texttt{RoCC} instruction sent from the Rocket core is not a simple command executed directly by the systolic array. Instead, it is a high-level, almost CISC-like directive, such as \texttt{LOOP\_WS} or \texttt{LOOP\_CONV\_WS}, that can encapsulate an entire deep learning layer computation. The fundamental design principle of Gemmini is to offload the immense complexity of interpreting this command from the CPU into a dedicated, multi-level hardware hierarchy.

This hardware-based command unrolling is a defining characteristic of a powerful, tightly-integrated co-processor. It autonomously handles tasks that would otherwise require thousands of CPU cycles—such as loop control, address calculation, and data dependency checking—freeing the host processor for other work. This section details the two primary levels of this unrolling hierarchy: \texttt{LoopConv} and \texttt{LoopMatmul}.

\subsection{Level 1: Convolution Decomposition (\texttt{LoopConv})}
\label{ssec:loopconv}

\begin{figure}[htbp]
    \centering
    \includegraphics[width=0.9\textwidth]{Gemmini_Internal_LoopConv.pdf}
    \caption{The \texttt{LoopConv} module. This is the first level of the command-unrolling hierarchy, responsible for decomposing a complex convolution operation into a series of matrix multiplication tasks.}
    \label{fig:loop_conv}
\end{figure}

The first stage in processing a high-level command is the \texttt{LoopConv} module (Figure~\ref{fig:loop_conv}), which functions as a Convolution Loop Unroller. Convolution operations involve complex, nested loops over batch dimensions (N), input/output channels (C), spatial dimensions (H, W), and kernel dimensions (R, S). Without hardware offloading, a programmer would need to manage this 6 to 7-dimensional loop nest, along with data tiling and resource allocation, in software.

The \texttt{LoopConv} module automates this entire process. It interprets a single high-level instruction (e.g., \texttt{gemmini\_loop\_conv\_ws}) and decomposes the complex convolution into a sequence of simpler matrix multiplication tasks. Its internal architecture is comprised of several parallel hardware units that handle the two distinct phases of the operation: data loading and execution.

First, the data loading phase is handled by three independent, concurrent units:
\begin{itemize}
    \item \textbf{\texttt{LoopConvLdInput}}: Loads input feature maps from memory.
    \item \textbf{\texttt{LoopConvLdWeight}}: Loads convolution kernel weights from memory.
    \item \textbf{\texttt{LoopConvLdBias}}: Loads bias values from memory.
\end{itemize}

Once the required data has been fetched, the execution phase begins, managed by two final components:
\begin{itemize}
    \item \textbf{\texttt{LoopConvExecute}}: Executes the convolution operation by passing tasks to the \texttt{LoopMatmul} module.
    \item \textbf{\texttt{Arbiter}}: A 5-to-1 arbiter that manages access to the memory interface, ensuring that the parallel load and execute units do not create resource contention.
\end{itemize}

These generated tasks are then passed down to the next level of the command-unrolling hierarchy.

\subsection{Level 2: Tiled Matrix Multiplication (\texttt{LoopMatmul})}
\label{ssec:loopmatmul}

\begin{figure}[htbp]
    \centering
    \includegraphics[width=0.9\textwidth]{Gemmini_Internal_LoopMatmul.pdf}
    \caption{The \texttt{LoopMatmul} module. This second-level unroller translates matrix multiplication tasks into a stream of smaller, tiled micro-operations for the physical hardware.}
    \label{fig:loop_matmul}
\end{figure}

The \texttt{LoopMatmul} module (Figure~\ref{fig:loop_matmul}) receives the sequence of matrix multiplication jobs from \texttt{LoopConv} and performs the second level of command unrolling. Its primary responsibility is to break these matrix-level operations down into smaller, fixed-size tiles that perfectly match the physical dimensions of the systolic array. This module is effectively a micro-code engine that processes five distinct types of operations—ranging from configuration (\texttt{CONFIG\_CMD}) and memory transfers (\texttt{LOAD3\_CMD}, \texttt{STORE\_CMD}) to the core computational directives (\texttt{PRELOAD\_CMD}, \texttt{COMPUTE\_CMD}). This section delves into the internal architecture and policies that allow it to manage this complexity.

\subsubsection{Internal Architecture and Decoupled Execution}

The internal structure of the \texttt{LoopMatmul} controller is composed of several independent hardware modules, each responsible for a specific part of the execution pipeline:
\begin{itemize}
    \item \textbf{\texttt{LoopMatmulLdA}}: Loads matrix A from DRAM to scratchpad memory.
    \item \textbf{\texttt{LoopMatmulLdB}}: Loads matrix B (weights) from DRAM to scratchpad memory.
    \item \textbf{\texttt{LoopMatmulLdD}}: Loads bias/accumulator data from DRAM to accumulator memory.
    \item \textbf{\texttt{LoopMatmulExecute}}: Performs the actual matrix multiplication computation.
    \item \textbf{\texttt{LoopMatmulStC}}: Stores results from the accumulator back to DRAM.
    \item \textbf{\texttt{LoopMatmulStCSpad}}: Stores results from the accumulator to scratchpad memory.
\end{itemize}

While these modules operate independently, they are coordinated through a lightweight handshake mechanism referred to in the design as iterator synchronization. For instance, the \texttt{LoopMatmulExecute} unit will not begin computation on a tile of data until it receives a signal that both \texttt{LoopMatmulLdA} and \texttt{LoopMatmulLdB} have successfully loaded the required operands into the scratchpad. This allows the \texttt{Load} modules to work ahead, fetching data for a future computation (\texttt{tile i+1}) while the \texttt{Execute} module is still busy processing the current one (\texttt{tile i}).

This decoupled architecture is a deliberate and critical design choice for overcoming the "memory wall". The high latency of fetching data from off-chip DRAM is a primary performance bottleneck in any accelerator. By overlapping the long-latency memory operations (Load and Store) with the core computation (Execute), the system effectively hides this latency. This ensures that the systolic array—the most valuable computational resource—is starved for data as infrequently as possible, maximizing its utilization and achieving a throughput which would be unattainable with a simple, rigid pipeline.

\subsubsection{Resource Management and Arbitration Priority}

The parallel operation of these internal modules inevitably leads to contention for shared resources. To manage this, the \texttt{LoopMatmul} controller employs a hardware arbiter that enforces a fixed-priority scheduling policy. This policy is not arbitrary; it is carefully designed to maintain pipeline flow and prevent deadlocks. The priority scheme is as follows:
\begin{enumerate}
    \item \textbf{Highest Priority - Store to DRAM}: Commands from the \texttt{LoopMatmulStC} module receive top priority. This is essential to prevent accumulator buffer overflow and free up internal resources for subsequent computations.
    \item \textbf{Execute Operations}: The \texttt{LoopMatmulExecute} module's preload and compute commands receive second priority to keep the systolic array actively computing.
    \item \textbf{Load Bias/Accumulator}: The \texttt{LoopMatmulLdD} module's commands for loading bias data receive third priority.
    \item \textbf{Load Input Matrices}: A weighted sub-arbiter manages requests from \texttt{LoopMatmulLdA} and \texttt{LoopMatmulLdB} modules with fourth priority.
    \item \textbf{Lowest Priority - Store to Scratchpad}: The \texttt{LoopMatmulStCSpad} module receives the lowest priority, as scratchpad stores are internal operations that are less critical to overall pipeline progression than DRAM transfers.
\end{enumerate}

This priority scheme ensures that result data is promptly written to DRAM to free accumulator resources, while maintaining sufficient data throughput to keep the computational units busy. The impressive result of this entire hierarchical process is that the \texttt{LoopMatmul} module transforms a single high-level command, like \texttt{LOOP\_WS(matmul 1024x1024)}, into \textbf{thousands} of precisely calculated, optimally ordered, resource-aware hardware operations ready for immediate execution by the back-end controllers.

\section{Decoupled Execution and Resource Management}
\label{sec:decoupled_execution}

The stream of primitive micro-operations generated by the command-unrolling hierarchy is not fed into a rigid, lock-step pipeline. Instead, Gemmini employs a more sophisticated and powerful paradigm: decoupled execution. This design allows the various stages of a complex operation—loading data, executing computation, and storing results—to proceed concurrently and asynchronously, managed by a central dispatch hub and a set of independent back-end controllers.

\subsection{The Reservation Station: A Central Dispatch Hub}
\label{ssec:reservation_station}

At the heart of the decoupled back-end is the Reservation Station. It receives a stream of commands from the \texttt{LoopMatmul} module that are far more than simple instructions; they are complete, resource-aware directives. These directives include optimally sequenced commands, complete address calculations for DRAM and scratchpad, resource-aware flow control to prevent buffer overflows, and attribution metadata for debugging. The Reservation Station's primary role is to act as a central orchestrator, managing data dependencies and dispatching these directives to the appropriate hardware units.

This enables a form of out-of-order execution, where a command can be dispatched as soon as its required data and hardware resources are available. The primitive commands it dispatches correspond to the fundamental actions of the accelerator pipeline, including loading data (\texttt{LOAD\_CMD}, \texttt{LOAD2\_CMD}, \texttt{LOAD3\_CMD}), preloading weights into the array (\texttt{PRELOAD\_CMD}), initiating the core computation (\texttt{COMPUTE\_AND\_FLIP\_CMD}), and writing results back to memory (\texttt{STORE\_CMD}).

\subsection{Back-End Controllers: Load, Store, and Execute}
\label{ssec:backend_controllers}

From the Reservation Station, primitive commands are dispatched to one of three specialized, independently operating back-end controllers. 

\begin{itemize}
    \item \textbf{\texttt{LoadController}}: Handles all data loading operations, fetching data from DRAM to the scratchpad memory.
    \item \textbf{\texttt{StoreController}}: Manages data storage operations, writing results from the scratchpad back to DRAM.
    \item \textbf{\texttt{ExecuteController}}: Orchestrates the actual computation, issuing commands to the systolic array and managing on-the-fly data transformations.
\end{itemize}

The \texttt{LoadController} and \texttt{StoreController} (Figure~\ref{fig:load_store_controller}) are focused exclusively on managing the high-latency operations of the memory hierarchy. The \texttt{ExecuteController} (Figure~\ref{fig:execute_controller}), however, contains a sophisticated collection of its own internal hardware modules, including the systolic array mesh itself, an \texttt{im2col} unit (Figure \ref{fig:im2col_module}), and various queues for command buffering. (A detailed breakdown of the \texttt{ExecuteController}'s internal sub-modules is provided in Appendix \ref{app:execute_controller_modules}).

This clear division of labor, orchestrated by the Reservation Station, is the cornerstone of the accelerator's performance. It allows long-latency memory operations and intense computation to overlap, effectively hiding the "memory wall" and ensuring the valuable systolic array is kept maximally utilized.

\section{The Physical Hardware: Compute and Memory}
\label{sec:physical_hardware}

The control-flow mechanisms described above orchestrate the work performed by the two foundational hardware components of the accelerator: the compute engine that performs the mathematical operations, and the memory subsystem that feeds it.

\subsection{The Processing Element (PE) and Distributed Arithmetic}
\label{ssec:pe_and_mac}

The fundamental building block of Gemmini's compute engine is the \textbf{Processing Element (PE)}. Each PE is a self-contained unit capable of performing a Multiply-Accumulate (MAC) operation, which is the core computation of a neural network. As shown in Figure~\ref{fig:pe_dataflows}, the PE is designed with the flexibility to support different dataflow strategies, such as Weight Stationary (WS) and Output Stationary (OS), allowing it to be optimized for different layer types.

\begin{figure}[h!]
    \centering
    \includegraphics[width=\textwidth]{Gemmini_Internal_PE.pdf}
    \caption{A single Processing Element (PE), the fundamental compute unit. It contains a Multiply-Accumulate (MAC) unit and the necessary logic to support multiple dataflows, such as Output Stationary and Weight Stationary.}
    \label{fig:pe_dataflows}
\end{figure}

A critical design choice in Gemmini is its approach to floating-point arithmetic. Gemmini avoids using a traditional, centralized Floating Point Unit (FPU). Instead, it implements a \textbf{distributed floating-point architecture} where arithmetic capabilities are embedded within every single PE. This is achieved through a powerful abstraction layer known as the \texttt{Arithmetic.scala} typeclass, which provides a full suite of IEEE 754-compliant operations by leveraging the Berkeley HardFloat library. The MAC unit at the heart of each PE (Figure~\ref{fig:mac_module}) utilizes this typeclass, effectively making every PE a specialized FPU. This design transforms the systolic array into a massively parallel floating-point computation engine, tailor-made for the demands of modern DNNs.

    \centering

    \caption{The Multiply-Accumulate (MAC) unit architecture. It is implemented using the \texttt{Arithmetic.scala} typeclass, which provides a suite of operations and supports multiple data types, including integers and IEEE 754 floating-point numbers.}
    \label{fig:mac_module}
\end{figure}

\subsection{The Tile and The Mesh: A Tale of Two Hierarchies}
\label{ssec:tile_and_mesh}

Individual PEs are not placed directly into a single large array. Instead, they are organized into a two-level hierarchy of \textbf{Tiles} and a \textbf{Mesh} (Figure~\ref{fig:mesh_configurations}). The design decision of how registers are used at each level is central to the entire accelerator's performance.

\subsubsection{The Tile: A Combinational Block of PEs}
A Tile is a two-dimensional array of PEs. The defining characteristic of a Tile is that it is \textbf{purely combinational}, meaning there are no pipeline registers between the PEs within a single Tile. This design choice, evident in the hardware generation code where PE inputs are connected directly, is made to minimize local latency and reduce the area and power overhead of registers. Grouping PEs into a combinational Tile allows for efficient broadcasting of input values to multiple PEs, promoting local data reuse.

\subsubsection{The Mesh: A Pipelined Systolic Array of Tiles}
The Mesh is a two-dimensional array of Tiles. Unlike the combinational logic within a Tile, the Mesh is \textbf{explicitly pipelined}, with shift registers placed between each Tile. This is the key that creates the systolic behavior of the entire array. These registers create the "systolic heartbeat," allowing waves of data to flow across the array in a controlled, rhythmic fashion. This pipelining between Tiles is what enables high throughput and scalability, as it breaks up long combinational paths and allows every Tile in the array to be actively computing on a different piece of data simultaneously.

\subsection{Architectural Trade-offs in Mesh Configuration}
\label{ssec:mesh_config_tradeoffs}

The Gemmini generator allows for configuring the hierarchy of the Mesh, offering a classic architectural trade-off between latency and clock frequency. For a system with a fixed number of PEs (e.g., 256), one can choose between having many small tiles or a few large tiles, as shown in Figure~\ref{fig:mesh_configurations}.

\begin{itemize}
    \item \textbf{Many Small Tiles (e.g., a 16x16 mesh of 1x1-PE tiles):} This configuration maximizes the number of pipeline stages. The combinational logic path within each stage is very short (just a single PE), which allows for a \textbf{higher maximum clock frequency}. However, it takes more clock cycles for a single piece of data to traverse the entire array, resulting in \textbf{higher pipeline latency}. This configuration is pipeline-optimized.

    \item \textbf{Few Large Tiles (e.g., a 4x4 mesh of 4x4-PE tiles):} This configuration has fewer, deeper pipeline stages. The combinational path within each stage is much longer (passing through multiple PEs), which limits the \textbf{maximum clock frequency}. However, an operation can pass through the entire array in fewer clock cycles, leading to \textbf{lower pipeline latency}. This configuration is throughput-optimized for batch processing.
\end{itemize}

The default configurations for Gemmini typically favor smaller (1x1) tiles, representing a design sweet spot that prioritizes high-frequency operation, which is often easier to implement and validate in a final ASIC or FPGA design.

\subsection{The Scratchpad: An Intelligent Memory Subsystem}
\label{ssec:scratchpad}

The Scratchpad (Figure~\ref{fig:scratchpad_module}) implements Gemmini's on-chip memory system, serving as the central data hub that bridges the gap between high-latency external DRAM and the high-throughput systolic array. Far more than simple storage, the Scratchpad is a sophisticated data movement engine with integrated processing capabilities, dual data paths, and complex arbitration logic, enabling the high-throughput, low-latency data access patterns essential for efficient matrix computation. Its design demonstrates the critical importance of specialized memory subsystems in achieving peak performance in domain-specific accelerators.

\begin{figure}[h!]
    \centering
    \includegraphics[width=\textwidth]{Gemmini_Internal_Scratchpad.pdf}
    \caption{The internal structure of the Scratchpad module, an intelligent memory subsystem with integrated DMA engines and data processing units that serves the systolic array.}
    \label{fig:scratchpad_module}
\end{figure}

The Scratchpad exposes two primary interfaces to the rest of the system: an \textbf{External Memory Interface} that connects to DRAM via the TileLink bus and DMA engines, and a \textbf{Compute Unit Interface} that provides direct, low-latency access for the systolic array.

Internally, its architecture is founded on a set of specialized \textbf{Memory Banks}. Multiple \texttt{ScratchpadBank}s store input data like weights and activations, with their banked structure enabling the parallel access patterns necessary for feeding the array. In parallel, dedicated \texttt{AccumulatorMem} banks store the higher-precision partial sums generated during computation, featuring integrated hardware to support activation functions and scaling operations.

Data movement between these internal banks and external memory is managed by dedicated \textbf{DMA Engines}, the \texttt{StreamReader} and \texttt{StreamWriter}. Critically, the Scratchpad contains several \textbf{Integrated Data Processing Units} that operate on data as it moves, a key design choice that significantly reduces CPU overhead. These units perform a range of on-the-fly transformations, including scaling for quantization, pixel repetition for convolution optimizations, and applying activation functions. (A detailed breakdown of these processing units is provided in \textbf{Appendix~\ref{app:scratchpad_units}}).

Ultimately, the sophisticated architecture of the Scratchpad—with its combination of banked memory, integrated data processing, and dedicated DMA engines—is a direct and powerful answer to the "memory wall" problem. It is an active, intelligent subsystem engineered not just to store data, but to transform and deliver it, ensuring the massively parallel Mesh is constantly supplied with operands and enabling the high-throughput computation that is the central goal of this work.

\section{Chapter Summary}

This chapter has provided a deep dive into the internal architecture of the Gemmini accelerator, tracing the path of a command from the RoCC interface to the physical compute units. We began by examining the two-level command-unrolling hierarchy, where high-level directives are translated into primitive micro-operations by the \texttt{LoopConv} and \texttt{LoopMatmul} modules. We then analyzed the decoupled execution model, orchestrated by the central Reservation Station, which allows for the concurrent operation of Load, Store, and Execute controllers to hide memory latency. Finally, we explored the physical hardware, including the distributed arithmetic in the Processing Elements and the configurable tile-and-mesh hierarchy of the systolic array. 

This detailed analysis of Gemmini's internal architecture completes the theoretical and design-level exploration of our system. The subsequent chapter transitions from this architectural blueprint to practice, documenting the complete implementation process—from SoC configuration and hardware generation to the final system deployment and testing on the target FPGA platform.
